# Runtime V2 多进程客户端冷启动对照

日期：2026-09-11；区域：us-west-2；镜像：500mb（实际约 500.63 MiB）。

## 结论

**改用 8 个独立 Python 工作进程后，500mb 的成功首调用 p50 在 c50/c100/c200 下均约 2.4–2.6 秒，不再呈现原单进程的 2.93 / 4.25 / 5.77 秒递增形态。** 这为“客户端实现显著影响原高并发 E2E”提供了证据，原来的增量不能全部归于 AgentCore 服务端或镜像大小。

但这不是 GIL 单因素实验：多进程、分进程连接池、事件保存方式和请求时序一起改变，成功接纳数也不同。只能报告**客户端方法改变后的观测差异**，不能宣称已证明 GIL 是唯一瓶颈或服务端纯冷启动耗时就是 2.5 秒。

| 并发 | 单进程成功 / 尝试 | 多进程成功 / 尝试 | 单进程 p50 / ms | 多进程 p50 / ms | 观测变化 |
|---|---:|---:|---:|---:|---:|
| 50 | 50/50 | 50/50 | 2931.4 | 2533.2 | −13.6% |
| 100 | 100/100 | 99/100 | 4250.6 | 2429.9 | −42.8% |
| 200 | 199/200 | 182/200 | 5774.9 | 2561.1 | −55.7% |

多进程共 **331/350** 首调用成功，**19 次 HTTP 429**，全部为 `New session creation rate exceeded`；没有其他首调用错误。不能省略限流，仅用成功请求的更低延迟宣布性能全面改善。

## 测试设计

- 运行窗口：**07:28:31–07:47:36 UTC**。c50、c100、c200 依次执行，每档单独新建一个 V2 Runtime，达到 READY、明确回显 `platformVersion=V2` 后进行一次 smoke，再静置 180 秒。
- 相同镜像 digest `sha256:8fce75a892c741d4712f9c3bdd2d0a8f429e69bebdd0393ea96c82f461029d87`，ECR 压缩体积 401,204,053 bytes。复用原角色、PUBLIC 网络、HTTP 协议、idle 60 秒、maxLifetime 600 秒，不修改 IAM、配额或镜像。
- 主机可用 CPU affinity 为 8 核。每档用 `multiprocessing.get_context("spawn")` 启动 **8 个全新工作进程**，各进程自行初始化 boto3 Session、凭证和数据面客户端；不继承父进程客户端或连接池。
- 进程内仍使用线程等待网络 I/O：c50 分配 7/7/6/6/6/6/6/6 个线程，c100 分配 13/13/13/13/12/12/12/12，c200 每进程 25 个。不是每请求一个进程，也不是把 200 个请求串行分给 8 个进程。
- 总连接池上限仍为 **2 × 并发**，即 100/200/400，分配到各工作进程。子进程不进行目标 Runtime 预热调用，smoke 在父进程执行，因此 worker 的连接从未用于 smoke。
- 父进程预先保存所有 session ID 及分配计划，所有客户端、线程就绪后通过包含父进程的全局 barrier 释放。请求 E2E 从自己的 SDK 调用前开始，到完整读取响应体结束；额外记录全局释放至完整响应，避免遗漏启动调度跨度。
- 仍立即对每个成功首调用做同 session warm，随后停止会话，与原负载一致。Warm/Stop 会与其他未完成首调用重叠；三档分别有 49/98/181 次 warm 在最后一个首调用完成前发起，不是独立的稳态 warm 压测。
- 禁止 SDK 自动重试，`total_max_attempts=1`。正常运行的事件只在进程内存中累积，全部工作进程的调用/停止完成后才进行结果 IPC 和文件保存。原单进程每次调用完成后会持锁追加 JSONL；这是额外的方法差异，可能影响其他尚未完成请求。
- SDK hook 只观察时间，不改变请求、响应或消费响应体。只保存结果元数据，不保存签名请求头或凭证。worker 失败的记录保留为不完整；超时会先终止/reap worker，再按计划处理未记录的停止并清理临时资源，不把失败场景当成有效延迟实验。

## 完整结果

延迟单位 ms；首调用分位数和均值只统计成功请求，smoke 不计入。沿用原报告对保存到 0.1 ms 的逐请求延迟做线性插值统计。

| 并发 | 成功 / 尝试 | 限流 | p50 | p90 | p95 | p99 | max | mean | Warm p50 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 50 | 50/50 | 0 | 2533.2 | 2895.9 | 2960.6 | 3025.5 | 3045.5 | 2579.8 | 101.1 |
| 100 | 99/100 | 1 | 2429.9 | 2843.2 | 2986.5 | 5385.9 | 5524.6 | 2545.0 | 105.9 |
| 200 | 182/200 | 18 | 2561.1 | 3083.3 | 3214.0 | 3394.8 | 3647.4 | 2618.2 | 103.9 |

331 个正式成功首调用均有成功 warm 和停止。3 个额外 smoke 也全部通过，首调用分别 2135.1 / 2255.9 / 2371.7 ms。

本次账号配额仍为新 session **25 TPS**、数据面 API **1000 TPS**、活跃 session **5000**。c100/c200 拒绝请求都明确报告新 session 创建速率超限，不能将 99/182 解释成 Runtime 同时运行容量上限，也不能从这次接纳率估算持续 TPS。

## 客户端时序与 CPU

### 起点跨度：多进程仍不等于严格同时发包

| 并发 | 单进程 API 计时起点跨度 / ms | 多进程 API 计时起点跨度 / ms | 多进程 before-send 跨度 / ms | 客户端首调用最大重叠数 |
|---|---:|---:|---:|---:|
| 50 | 74.8 | 264.9 | 263.8 | 50 |
| 100 | 433.7 | 541.3 | 540.1 | 100 |
| 200 | 1623.0 | 1224.4 | 1223.3 | 194 |

运行前设定 before-send 跨度 ≤100 ms 为紧凑突发目标，**三个档位均未达到**。结果没有丢弃或自动重跑；该目标是负载形态验收，不是数据完整性校验。本次不能称为理想的 50/100/200 请求同时抵达服务端。

尤其 c50/c100 的起点跨度反而更大，但成功首调用 p50 更低，说明不能把全部 E2E 差异简单解释为“请求发得更齐”。c200 还存在成功样本接纳量变化。

### SDK 分段时间（成功首调用中位数）

| 并发 | API 开始至 before-send | before-send 至 response-received | response-received 至完整读完 body | 全局释放至完整读完 body |
|---|---:|---:|---:|---:|
| 50 | 0.821 ms | 2530.141 ms | 0.206 ms | 2557.303 ms |
| 100 | 0.820 ms | 2428.723 ms | 0.260 ms | 2627.796 ms |
| 200 | 0.847 ms | 2558.653 ms | 0.207 ms | 3184.788 ms |

这些中位数分别计算，**不能直接相加重建总 p50**。局部已安装 botocore 源码确认：

- `before-send` 位于请求准备/签名之后、HTTP transport `_send` 之前，不是 socket 实际发包时间；其后仍可能发生连接获取、DNS/TCP/TLS、网络等待等。
- `response-received` 在 SDK 收到并解析响应之后发出，成功流式响应此时未必已读完 body；错误响应可能已缓冲。它不是精确 TTFB，也不是服务端处理完成时间戳。
- 因此中间约 2.4–2.6 秒包含网络、连接、服务端及 SDK 响应处理，**不是纯 AgentCore 执行耗时**。旧单进程实验没有这些 hook，无法直接逐段相减归因。
- c200 全局释放到完整响应中位数约 **3.18 秒**，高于请求自身 E2E 中位数 2.56 秒；若关心整批任务的体验，应保留这个区别。

### 客户端资源

| 并发 | 8 个 worker CPU 时间合计 | worker 各自峰值 RSS 之和 |
|---|---:|---:|
| 50 | 2.3633 CPU-s | 490.25 MiB |
| 100 | 5.2001 CPU-s | 581.25 MiB |
| 200 | 12.3775 CPU-s | 657.59 MiB |

CPU 时间从各 worker 客户端就绪后、线程启动前采集，至该 worker 请求结束并退出线程池，包含线程准备、首调用、warm、停止等，不含客户端初始化和最终 IPC。它不是首调用阶段单独 CPU，也不是瞬时 CPU 利用率。RSS 为每进程生命周期峰值相加，峰值未必同时发生；不能当作同一时刻的总 RSS。旧单进程没有同口径 CPU 数据，无法声称节省了多少 CPU 或证明某个核心原先饱和。

## 验证与资源清理

- 每档独立记录 8 个 PID，三档共 24 个工作进程全部正常退出，所有客户端在全局 barrier 释放前就绪；每个 session 固定在一个工作进程内完成首调用、warm 和停止。
- 共 **353 个唯一 session ID**（350 个正式尝试 + 3 个 smoke）、**1,040 条 API 事件**：353 次首调用、334 次 warm、353 次停止。331 个正式成功 session 加 3 个 smoke 的 **334 次停止返回 HTTP 200**；19 个限流 session 停止返回 `ResourceNotFoundException`，不标为停止成功。
- 独立 `verify_multiprocess_coldstart.py` 重算统计，检查完整计划、PID/索引/session 对应、API 次数、零重试、hook 顺序、源 hash、V2/配置一致与资源删除。完整记录通过校验，紧凑突发目标未达则单独报告。
- 5 项离线测试通过，包含三个档位的实际 `spawn` + 假传输完整运行，以及进程初始化失败、崩溃、挂起与错误/流式响应 hook。先读取 IPC 再 join，测试结果大于管道缓冲区仍能收集；所有失败实验均未标为完成。
- 三个本次临时 Runtime 各轮后即删除；07:47 UTC 再次只读查询均为 `ResourceNotFoundException`。原 Runtime、镜像、角色、配额和历史证据未修改；自动生成日志未删除，可能保留存储费用。
- 运行器退出码 **1**：`measurement_complete=true`、`cleanup_complete=true`、`all_invocations_successful=false`。存在真实限流，所以不称为全部请求成功，也不因退出码 1 丢弃已完整采集的数据。
- 强制终止、create 响应丢失或本地存储失败仍可能需要人工恢复。保存的 `create_inflight` 和请求 token 不明时须先只读核对，不能盲目重复创建。worker 异常路径的 IPC 可能与其他未结束流量重叠，该类失败结果不用于延迟结论。

## 解释边界与下一步

1. **此次仅测 500mb。** 多进程 500mb p50 接近先前单进程 1gb/2gb 的 2–3 秒范围，削弱了“小镜像天然更慢”的解释，但没有做多进程三镜像随机顺序比较。
2. **不能归因于 GIL 一项。** 进程数、每进程线程数、连接池分布、凭证初始化以及日志保存方式均发生变化；GIL、TLS、调度、文件写入、服务端状态的贡献尚未拆分。更低的 p50 不意味着“从 AgentCore 里消除了 3 秒”。
3. **各组接纳数和负载形态不同。** c200 单进程成功 199、多进程成功 182；c50/c100 发起跨度反而变大。需同时比较失败率、分位数和全局释放后的完成时间，不能只比较成功样本 p50。
4. **每档仅一轮、按顺序执行，且比较跨运行时刻。** 不是随机 A/B，也没有统计置信区间。多进程各档使用独立新 Runtime 与新 worker，消除了跨档客户端连接继承，但没消除平台容量和缓存状态变化。
5. **新 session 不证明完整冷启动。** 仍保留历史进程年龄启发式，不能从 `fresh_boots=0` 判定全部命中预热，也不能把 before-send 到 response-received 当作 microVM 启动耗时。
6. **后续最有价值的对照**是使用同一套内存缓冲记录/hook 客户端，交替运行 1 个与 8 个进程，并让两组都使用相同总连接容量、相同成功负载目标及重复轮次；再结合 TCP/TLS 或服务端 tracing。增加轮次、调整配额、额外部署均需新的授权，本次未自动追加。

参考：[原单进程测试与补测](COLDSTART_V2_REPORT.zh.md)、[AgentCore 配额文档](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/bedrock-agentcore-limits.html)。
