# AgentCore Runtime V2 coldstart 验证报告 · v3

日期：2026-09-17（UTC）。v3 是本报告版本，不是 Runtime 平台版本。

## 结论

**公开 boto3/botocore 1.43.96 已能创建并调用 Runtime V2；15 格完整复测完成，但不是全部请求成功。** 1,083 次正式首调用中 **841 成功（77.65%）、242 次 HTTP 429（22.35%）**，均为 `New session creation rate exceeded`，无其他首调用错误。

- 12 个并发格（c10–c200）的成功首调用 p50 为 **2.206–2.543 秒**；三个 c1 单次值为 **2.542 / 2.470 / 3.469 秒**。正式成功样本最大值 **4.042 秒**，无超过 5 秒的样本。
- 相较 9 月 11 日 beta 多进程基线，各并发格成功首调用 p50 降低 **2.6%–13.4%**，但整体接纳率从 **86.61% 降至 77.65%**。不能据此宣称 GA 全面提速或归因为 boto3 升级。
- 841 次正式 warm 全部成功；含 15 个 smoke 的 **856 个成功会话均停止成功**。15 个临时 Runtime 均已删除，并经独立 AWS 查询确认不存在。
- 运行器退出码 **1**，原因是存在真实限流；`measurement_complete=true`、`cleanup_complete=true`、`all_invocations_successful=false`。离线证据核验通过，不等于所有请求成功。

运行窗口：**14:46:42–14:58:48 UTC**，约 12 分钟。仅测 `us-west-2`，单轮固定顺序，结果不是延迟或吞吐 SLA。

## 公开 SDK 与验证范围

本轮按用户告知的 Runtime V2 GA 进行复测。独立核实的是**公开 SDK 已支持配置 V2，以及本账号、本区域的实际运行结果**；未以其他 AgentCore 功能的 GA 公告替代 Runtime V2 的发布公告，也不从单账号测试推断所有账号、所有区域均已开放。

- 环境升级：项目 `.venv` 从私有 boto3/botocore **1.43.87** 升至公开 PyPI 最新 **1.43.96 / 1.43.96**；不修改系统 Python。
- [botocore 更新日志](https://github.com/boto/botocore/blob/1.43.96/CHANGELOG.rst)：1.43.95 加入 Create/Update/GetAgentRuntime 的 `platformVersion`；1.43.96 加入 Runtime/Endpoint 的 `DELETE_FAILED` 状态。本轮对三个操作均检查到该字段。
- 运行前查询 [PyPI boto3 元数据](https://pypi.org/pypi/boto3/json)，并下载版本化的官方 botocore wheel。核验 wheel SHA-256，再逐个比对实际加载的控制面、数据面 service model 与 wheel 内的 JSON，两者一致。`AWS_DATA_PATH` 未设置，模型搜索路径也保存在证据中；因此不仅是“版本号看起来已升级”。
- 创建请求仍明确设置 **`platformVersion="V2"`**，不依赖默认值。未实测 Update 路径、默认平台选择、其他区域或 V1 对照。
- 区域 `us-west-2`，账号 `434444145045`。15 格全部新建 Runtime、全部重新采样，未将 beta 样本混入 v3。历史入口与证据保持不变。

详细来源与模型 hash：[`coldstart_v3_2026-09-17/sdk.json`](coldstart_v3_2026-09-17/sdk.json)。最新版本是本轮查询时的结果，不代表未来仍为最新。

## 测试设计与计时口径

本轮沿用 2026-09-11 多进程矩阵的负载和计时实现，仅用新入口替换“beta 前置检查及三格历史复用”逻辑，以保留可比性。

| 配置 | 本轮设置 |
|---|---|
| 镜像标签 | 500mb / 1gb / 2gb，均按历史 digest 固定，不重新构建 |
| ECR 压缩大小 | 401,204,053 / 950,825,808 / 1,922,103,892 bytes |
| 角色与网络 | 原 `AgentCoreColdstartRole`；PUBLIC / HTTP |
| 会话生命周期 | idle 60 秒，maxLifetime 600 秒 |
| 矩阵 | 三种镜像 × c1/c10/c50/c100/c200；每格一轮，样本数等于并发，共 1,083 次正式首调用 |
| 客户端 | `min(8, c)` 个 spawn 进程，进程内线程，独立 boto3 Session、凭证和连接池；总连接池容量 `2 × c` |
| 发起方式 | 所有线程与父进程通过全局 barrier 释放；进程初始化不计入单请求 E2E |
| SDK 重试 | `total_max_attempts=1`，首调用失败不补发 |
| 会话后续 | 成功首调用立即同 session warm；所有尝试均调用 StopRuntimeSession |
| 记录方式 | hook/事件先缓存在内存，所有 worker 流量结束后再集中保存结果 |
| 执行顺序 | 500mb、1gb、2gb；各自从 c1 递增到 c200，不随机化 |

所有 Runtime 创建后依次等到 Runtime 与 DEFAULT endpoint READY，并执行独立 smoke；最后一个 smoke 停止后静置 180 秒，再开始正式矩阵。每格完成后删除其 Runtime 并等待删除确认，另暂停 10 秒再进入下一格。较后格的 smoke 后静置时间因此更长；本轮没有新增每格 180 秒的限流恢复等待。

**计时是新 session 首调用端到端延迟**：从进入 SDK 调用前到完整读完响应体，包含连接、客户端、网络、平台和应用处理；不含部署等待。它不是服务端独占时间，也不是已经证明的 microVM 启动或全镜像下载耗时。镜像中的 padding 不由应用读取，不代表大模型加载负载。

`before-send` 是 SDK 传输前 hook，不是网络实际发包时刻；记录跨度用于判断负载是否接近紧凑突发。warm/stop 会与其他未完成的首调用重叠，因此 warm 不是独立稳态测试。历史 `fresh_boots` 启发式只为兼容保留，不据此认定隔离实例的冷暖状态。

当前账号区域配额为：新 session **25 TPS**、数据面 API **1,000 TPS**、活跃 session **5,000**。不修改配额，不将名义 c200 解释为 200 TPS，也不从一次突发接纳数推算容量上限。

### 发起跨度与客户端并发

下表为 SDK `before-send` 跨度（ms）。c1 的跨度为 0，没有并发紧凑度意义。

| 镜像 | c10 | c50 | c100 | c200 |
|---|---:|---:|---:|---:|
| 500mb | 5.154 | 129.951 | 524.341 | 1268.258 |
| 1gb | 5.007 | 196.301 | 491.604 | 1065.587 |
| 2gb | 5.430 | 210.558 | 520.490 | 1554.095 |

三个 c10 达到预设 ≤100 ms 目标；九个 c50+ 均未达到。c200 首调用最大在途重叠数分别为 **183 / 167 / 164**，不是严格同时抵达服务端的 200 请求。不能从单请求耗时中扣掉整批发起跨度来计算“纯服务端冷启动”。客户端 Python 3.12.3、CPU affinity 为 8 核，与历史多进程测试的可用核数一致。

正式请求实际发生在各自 smoke 停止后的 **243.7–451.2 秒**。成功响应中 `request_ts - proc_start_ts` 为 **349.6–604.0 秒**，出现 27 个不同的 `proc_start_ts`；因此这些字段不能证明每个新 session 都触发新的进程启动，也不能据此推断不同 session 共用同一隔离实例。

## 与 beta 基线的比较

主基线为 [2026-09-11 完整多进程矩阵](coldstart_v2_matrix_2026-09-11/matrix.json)：相同区域、角色、镜像 digest、会话配置和客户端测量实现，私有 SDK 1.43.87；其中 500mb/c50/c100/c200 复用了当天更早的多进程实验。v3 所有格均为本轮新测。

下表为并发格成功首调用 p50 的观测变化；**百分比只描述跨时段结果，不是 SDK 或 GA 的因果收益**。

| 镜像 | c10 | c50 | c100 | c200 | beta 成功/尝试 | v3 成功/尝试 |
|---|---:|---:|---:|---:|---:|---:|
| 500mb | −2.6% | −9.4% | −6.0% | −9.2% | 342/361 | 331/361 |
| 1gb | −11.7% | −8.5% | −7.3% | −8.8% | 337/361 | 259/361 |
| 2gb | −13.4% | −10.8% | −9.2% | −4.8% | 259/361 | 251/361 |
| 合计 | — | — | — | — | **938/1083** | **841/1083** |

成功/尝试汇总含 c1；c1 样本太少，不参与“整体提速”结论。beta 的 2gb/c1 唯一请求被限流，无法与本轮的 3.469 秒作延迟对比。

**本轮接纳数减少 97，429 从 145 增至 242，接纳率下降约 8.96 个百分点。** 本轮每个并发格的成功样本 p50 虽然较低，但接纳样本数、发起时序、日期、平台状态与账号共享配额都可能影响比较。固定执行顺序也可能让后续 1gb/2gb 格受到前序流量影响；10 秒间隔不保证配额恢复，不能把限流或延迟差异单独归因于镜像大小。

9 月 13 日的长尾重复实验另测 500mb/c100 与 2gb/c200 各三轮，曾出现 5.333 秒最大值。本轮未复做三轮重复、不合并那批样本；无 >5 秒样本只能说明本轮没有观测到，不能宣布长尾问题已经解决。若要归因平台或 SDK，需要跨时段重复、控制接纳负载和客户端实现的配对实验，本次未扩大测试范围。

## 验证与资源清理

- `verify_coldstart_v3.py` 独立检查全部 **15 个新格、1,098 个唯一 session ID**（1,083 正式 + 15 smoke）、请求/进程分配、原始事件、响应体、无重试、统计值、镜像/配置/V2 回显、源码 hash 和删除记录。退出码 **0**；包含 postcheck 的最终结果保存在 [`final_verification.log`](coldstart_v3_2026-09-17/final_verification.log)。
- 共 **99 个 spawn worker** 正常退出，无进程失败。含 smoke 共 **3,052 条数据面事件**：1,098 次首调用、856 次 warm、1,098 次停止。856 次停止 HTTP 200；242 个被限流 session 的停止返回 `ResourceNotFoundException`，不标为停止成功。
- 15 个 Runtime 的 create 请求均指定 V2，GetAgentRuntime 的 READY 响应均明确回显 V2；15 个 smoke 的首调用、warm、停止均成功。
- 运行器逐格确认删除，最后一次删除确认在 **14:58:38 UTC**。`verify_coldstart_v3_cloud.py` 于 **14:59:33 UTC** 完成独立只读查询，15 个 Runtime 均返回 `ResourceNotFoundException`；请求 ID 与结果保存在 [`postcheck.json`](coldstart_v3_2026-09-17/postcheck.json)。未删除既有 Runtime、镜像、角色或日志组，自动生成的 CloudWatch 日志可能仍有存储费用。
- 额外检查了**实际 boto3 Session 的 loader**，包括 profile 中的 `data_path`，而非仅检查独立 `Loader()`。本机环境与配置的覆盖路径均为空，实际控制/数据面模型与官方 wheel hash 一致。测量入口已冻结以保留源码 hash；其初始 provenance 检查单独不能排除 profile 覆盖，未来复测也应执行此项实际 Session 检查。
- 新增 SDK/全新矩阵的 3 项离线测试，加上原矩阵和多进程的 9 项测试，共 **12 项通过**，包括实际 spawn 与模拟传输、初始化失败、进程崩溃和挂起的回收。输出见 [`offline_tests.log`](coldstart_v3_2026-09-17/offline_tests.log)。`pip check`、新脚本语法检查、diff 空白检查通过。

运行器的退出码 1 原样保留，不因核验通过改成 0；它反映请求层面的真实限流，不表示测试或清理未完成。强制终止、创建响应丢失或本地保存失败仍可能需要人工恢复；入口保留 `create_inflight` 等状态，不承诺所有异常路径都能自动清理。

```bash
  --out results/coldstart_v3_NEW_RUN

# 新运行测量与清理均完成后，先只读查询 AWS，再离线验收

.venv/bin/python -B verify_coldstart_v3.py results/coldstart_v3_NEW_RUN
```

`verify_coldstart_v3_cloud.py <新一轮证据目录>` 会读取 AWS、核对实际 Session 模型，并新增不可覆盖的 `postcheck.json`；不是离线命令，不要对已有该文件的目录重复执行。它不删除资源。

入口拒绝覆盖已有目录，目录必须位于项目内；运行器以 0700/0600 权限创建目录与原始证据。SDK 前置检查要求运行时安装版本等于 PyPI 当时的最新版，因此未来用固定 1.43.96 重放时可能被拒绝；历史证据的离线验证不依赖在线 PyPI，也不要求当前安装版本仍等于历史版本。

证据目录：[`coldstart_v3_2026-09-17/`](coldstart_v3_2026-09-17/)。根目录的 `matrix.json` 包含版本、环境、配额、请求、镜像、部署、源码 hash 和完成状态；每格保存 `client_plan.json`、`client_result.json`、`raw.json`、`summary.json`、`smoke.json`、`cleanup.json`。`run.log` 保留过程与错误。
