# AgentCore Runtime V2 冷启动测试报告

## TL;DR

**us-west-2 的 V2 测试覆盖三档镜像（约 501 / 1025 / 1951 MiB）和四档并发（1/5/10/50），300 次正式探测全部成功，无错误或限流。** 新 session 首次调用整体 **p50 为 2.25 秒、p90 为 3.09 秒，最大值为 5.19 秒**；各镜像与并发组合的 p50 为 **2.15–2.99 秒**，本次未观察到延迟随镜像大小明显递增。300 次同 session 的 warm 跟测全部成功，整体 **p50 为 107.5 ms**。这里测量的是首次调用的端到端响应时间，不是单独的底层 microVM 启动耗时。

## 结论

**V2 完整矩阵 300/300 成功，无首次调用错误或限流；300 次 warm 跟测也全部成功。首次调用整体 p50 为 2,250.3 ms，p90 为 3,085.2 ms，最大值 5,192.1 ms；warm 整体 p50 为 107.5 ms。** 3 个额外部署后 smoke 全部通过；303 个 session 均停止成功，3 个临时 Runtime 均已删除并确认不存在。

最重要的变化是分布发生了改变，而不是所有场景都变快：

- **高并发首次调用更快**：c=10 的 V2 p50 为 2.15–2.21 秒，相较历史 7.32–13.46 秒降低 **70.5%–84.0%**；c=50 的 V2 p50 为 2.19–2.99 秒，相较历史 8.15–13.49 秒降低 **63.4%–83.8%**。
- **低并发首次调用更慢**：c=1/5 的历史 p50 为 0.41–1.18 秒，本次为 2.15–2.48 秒，耗时约为历史的 **1.92–5.21 倍**。不能用高并发改善掩盖低并发退化。
- **本次没有复现历史上随镜像大小明显增加的首次调用中位数**：同一并发下 1gb / 2gb 并未比 500mb 系统性更慢；c=50 反而是 500mb 较高。这是单次观测，不证明镜像大小对 V2 永远无影响。
- **Warm 没有改善**：各单元格 p50 为 104.2–128.2 ms，高于历史 68.6–101.5 ms；整体 107.5 ms 对比历史 75.0 ms，约增加 **43.3%**。

运行窗口：**2026-09-11 01:45:49–01:58:35 UTC（北京时间 09:45:49–09:58:35）**；正式矩阵为 01:52:43–01:58:29 UTC，约 5 分 46 秒，其余时间用于部署、smoke、静置和清理。历史比较是跨日期的描述性对照，不是当天 V1/V2 随机 A/B 实验。

### 测量口径

直接复用原 `coldstart_test.py` 的 `probe`、`run_cell`、客户端配置及统计函数，不复制其压测实现。本次适配器仅负责 V2 部署、隔离输出、保存完整响应以及校验 HTTP 200 / `pong` / 数值时间戳；这些额外操作位于原计时区间之外，但会略微影响每轮请求结束后的调度。

1. **新 session 首次调用 E2E（主指标）**：每个探针使用全新 40 字符 `runtimeSessionId`，计时从发起 `InvokeAgentRuntime` 到完整读取响应体。下文表格中的“首次调用”均指此指标，不等价于已确认发生底层 microVM 启动。
2. **Warm 跟测**：每次首次调用返回后，立即复用同一 session 再调用一次，随后调用 `StopRuntimeSession`。Warm 跟测没有独立同步屏障，可能与其他线程的首次调用重叠，不是单独的稳态吞吐测试。
3. 关闭 botocore 重试：`total_max_attempts=1`，读超时 300 秒、连接超时 30 秒，最大连接池 100。并发线程通过 `threading.Barrier` 同时释放。
4. 完整矩阵：500mb / 1gb / 2gb，各运行 c=1 的 10 轮、c=5 的 4 轮、c=10 的 2 轮、c=50 的 1 轮。每镜像 100 个新 session，共 **300 个矩阵样本**，轮间暂停 5 秒。
5. 三个 Runtime 分别做一次部署后 smoke（首次调用 + warm），不计入矩阵；全部 smoke 完成后统一静置 180 秒。之后按镜像 500mb → 1gb → 2gb、并发 1 → 5 → 10 → 50 顺序测试。READY 和部署耗时不计入首次调用 E2E。
6. 分位数沿用原脚本的线性插值算法；首次调用延迟只统计成功样本，失败次数另列。不同单元格不混用输出目录。

## 进程时间戳与冷启动判定的边界

原脚本保留的 `fresh_boots` 字段计算如下：

```text
(request_ts - proc_start_ts) × 1000 < cold_ms
```

它比较进程年龄与客户端 E2E 时长，是一个**进程年龄启发式**，不是平台提供的冷启动标记：

- 新 session 只确保本次客户端未主动复用已有 session，并不能强制清空主机缓存、预备实例或镜像缓存。
- 如果某种实现会恢复包含进程状态的快照，`proc_start_ts` 可能来自快照制作时刻；一次按需恢复也可能被旧规则判为“非 fresh”。**本测试不能据此确认 V2 使用了快照，也不能由 `fresh_boots=0` 推断没有冷启动或全部命中预热池。**
- `proc_start_ts` 较新也不证明发生了完整镜像拉取、microVM 创建；而原始 `wall_start_iso` 在并发屏障之前记录，不能拿它精确替代实际 API 发起时刻。

本次 300 个矩阵样本的旧 `fresh_boots` 均为 0，每种镜像的 100 个新 session 只出现 **2 个不同的 `proc_start_ts` 值**；进程年龄范围分别约为 330–442 秒、441–555 秒、547–657 秒。重复的进程启动时间戳说明不能把这个字段简单当作 V2 的独立实例 ID，更不能据此认定只启动了 2 台 microVM。

因此本报告以完整新 session 首次调用分布为主，不将 V2 样本按该启发式直接命名为“真实启动 / 预热命中”。原始时间戳和旧字段保留供复核。

### 比较限制

历史数据来自 **2026-07-09** 的原 AgentCore Runtime 测试；其部署脚本没有显式传入 `platformVersion`。本报告将其标为“V1（历史）”作为历史基线，不把旧记录当作当天已核验的 V1 控制组。历史 c=1/10/50 在约 06:05–06:12 UTC 运行，c=5 是约 06:27–06:29 UTC 的后续补测；本次顺序、部署后等待和池状态并非完全一致。

同区域、相同工作负载与样本设计提升了可比性，但日期、SDK、服务端实现、资源调度和缓存状态仍是混杂因素。百分比表示**相对历史观测值的差异**，不单独证明 V2 的因果性能收益。c=50 只有一轮突发，50 个请求并不等于 50 次独立容量实验；不能据此宣称性能 SLA 或镜像大小在所有负载下均无影响。汇总数据中 c=50 占一半样本，也不代表实际业务的并发分布。

历史延迟统计排除了 2 个失败样本，其中一个是初始化超过 120 秒的 `RuntimeClientError`，另一个是限流；失败记录没有 `cold_ms`。所以历史最大成功延迟并不是所有请求的最坏等待时间。

