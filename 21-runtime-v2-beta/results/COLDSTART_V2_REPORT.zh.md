# AgentCore Runtime V2 多进程冷启动测试报告

## TL;DR

**本次多进程测试中，成功被接纳的新 session 首调用延迟总体较稳定，没有随镜像大小或并发档位升高而明显增长。** 在 500mb、1gb、2gb 镜像及 1/10/50/100/200 并发矩阵中，有成功样本的各组首调用中位数／单次值集中在 **2.4–2.9 秒**，并发组的 p90 约 **2.6–3.1 秒**，Warm 中位数约 **0.1 秒**。但“成功请求的典型延迟稳定”不等于“所有请求都能稳定启动”：1083 次尝试中有 **145 次（13.4%）因新 session 创建速率限制被拒绝**，最大成功延迟达到 **5.82 秒**。因此，当前结果支持 **V2 在此次轻量 ping-pong 负载下具有较稳定的成功首调用延迟，扩展时需重点关注接纳速率限制**；由于每个组合仅一轮、存在限流筛选和客户端发起跨度，尚不能据此保证长期稳定性或性能 SLA。

## 摘要

本报告只使用 **2026-09-11、us-west-2** 的多进程矩阵：**500mb / 1gb / 2gb × 并发 1 / 10 / 50 / 100 / 200，共 15 格，每格一轮**。其中 12 格新测，500mb 的 c50/c100/c200 复用同日已完成的多进程原始证据，不重复发起请求。

**1083 次正式首调用尝试：938 成功、145 次新 session 创建速率限流，无其他首调用错误。** 成功首调用全部完成同 session warm 跟测；另有 15 次成功 smoke，不混入正式延迟统计。测量和清理均完整，但不是所有请求成功。

- 有成功样本的单元格，首调用 p50／单次值为 **2413.7–2869.7 ms**；Warm p50／单次值为 **101.1–138.2 ms**。它们是各格统计值的范围，不是合并分布。
- **2gb/c1 唯一一次尝试被限流，没有成功延迟可报告**，不记作 0 ms，也不补跑。全部 c1 都只有一个尝试，不能据此估计尾延迟。
- 并发单元格中，只有三个 c10 的 `before-send` 跨度达到 ≤100 ms；全部 c50/c100/c200 未达到。c1 跨度为零只是单请求的必然结果，不构成突发验证。
- 这是**新 session 首次调用 E2E**，不是已确认的 microVM 启动耗时。共享配额、固定执行顺序、不同等待时长及复用批次的时间差，限制了镜像大小和并发扩展性的因果判断。

总清单与核验入口：[`coldstart_v2_matrix_2026-09-11/matrix.json`](coldstart_v2_matrix_2026-09-11/matrix.json)、[`verify_coldstart_v2_matrix.py`](../verify_coldstart_v2_matrix.py)。

## 环境与测量方法

- 区域 **us-west-2**，账号 `434444145045`；私有 boto3 / botocore **1.43.87**，Python **3.12.3**；新运行记录的客户端 CPU affinity 为 0–7。
- 每格使用独立临时 Runtime，均在 READY 后核验 `platformVersion="V2"`。统一为 **PUBLIC / HTTP**、`idleRuntimeSessionTimeout=60`、`maxLifetime=600`，角色为 `AgentCoreColdstartRole`。
- 工作负载仅为 ping-pong 探针，校验 HTTP 200 / `pong` 和完整响应，不调用 LLM。大镜像通过 padding 增大，应用不读取这些填充内容；不能代表启动时加载大模型或大量业务文件的应用。

### 多进程与样本口径

1. 每格只运行一轮，正式首调用尝试数等于并发 `c`。工作进程数为 **`min(8, c)`**：c1 使用一个 `spawn` 子进程、一个样本；c10/c50/c100/c200 均使用 8 个 `spawn` 工作进程。全矩阵共 **99 次工作进程启动（新测 75、复用 24）**，不是 99 个同时运行的进程。
2. 每个进程独立创建 boto3 客户端、连接池和线程池；线程总数为 c，连接池配置总容量为 **2×c**。父进程预先分配请求索引和唯一 session ID，所有工作线程通过跨进程全局屏障一起释放；不在工作进程间共享 boto3 客户端。
3. SDK **`total_max_attempts=1`**，不重试、不补样。成功首调用后立即在同 session 发起 warm，再停止该 session；限流的 session 也尝试停止。Warm/stop 按 session 独立推进，可与其他首调用重叠，不是另一次同步 warm 突发或稳态吞吐测试。
4. **首调用 E2E** 从该请求调用 SDK 前计时，到完整读取响应体结束；部署、等待 READY、smoke、静置及屏障前等待不计入。响应/错误事件先保存在进程内存，所有工作进程完成流量阶段后才汇集并持久化。
5. [`matrix_multiprocess_client.py`](../matrix_multiprocess_client.py) 复用已冻结的工作客户端，在流量完成后、持久化前明确为结果行赋镜像标签；不更改延迟、响应或错误。现有工作客户端源码 hash 保持不变，清单记录源码及复用证据的 SHA-256。
6. 延迟只统计成功样本，失败计入尝试分母并单列。分位数按线性插值计算，独立 verifier 用标准库重算。c1 的成功值只是单次观测；不报告其 p90/p95。没有成功样本时使用 **N/A**。

## 执行时间线与等待条件

所有时间均为 **2026-09-11 UTC**。复用三格的正式流量窗口为 **07:34:43–07:47:30**；新运行从 **08:15:32** 开始，到 **08:26:40** 完成，12 格正式流量窗口为 **08:22:49–08:26:25**。正式流量窗口包括各 session 的首调用、warm 和 stop，不包括 Runtime 部署。

新运行先创建全部 12 个 Runtime，再依次等 READY 并串行执行各格 smoke；**最后一个 smoke 停止后统一等待 180 秒**，然后串行运行正式单元格。固定顺序如下：

```text
500mb: c1 → c10
1gb:   c1 → c10 → c50 → c100 → c200
2gb:   c1 → c10 → c50 → c100 → c200
```

每个新测单元格完成后删除对应 Runtime，再暂停 10 秒。该流程避免本运行的正式突发彼此重叠，但**不保证账号共享配额恢复到相同状态**，也不代表所有单元格恰好静置 180 秒。

独立 verifier 以各格 smoke 的 stop 完成时间到第一条正式 SDK 调用开始时间重算等待：复用三格为 **180.275–180.403 秒**，新测 12 格为 **248.742–388.371 秒**。新测后面的格还经历前面格的流量与清理，不能把“本 Runtime 距 smoke 的等待”当作“全账号没有流量的恢复时间”。清单中的 `observed_settle_seconds` 在启动工作进程前记录，因此略小于此处的实际首调用等待。

## 限流解释与结果边界

145 次正式失败全部为 **`ThrottlingException` / HTTP 429 / `New session creation rate exceeded`**。清单记录本次账号、区域配额如下；没有调整配额：

| 配额 | 记录值 |
|---|---:|
| 新 Runtime session 创建速率（L-8EE2AEA2） | 25 TPS |
| Runtime 数据面 API 速率（L-46ED137C） | 1000 TPS |
| 账号活跃 session 数（L-3E5722B2） | 5000 |

错误明确指向**新 session 创建速率**，不是镜像启动错误，也不是达到活跃 session 容量上限的证据。配额由账号共享；一次突发接纳超过 25 个请求，不能解释为持续 TPS 配额提高。成功数也不能用于推断最大并发容量。

特别是 **2gb/c1**，它在固定顺序中紧接 **1gb/c200**（沿用删除和 10 秒暂停流程），唯一首调用得到 429，未重试。该格测量完整但无成功延迟；不能将其写成“2gb 单请求也无法启动”，或把原因归于镜像大小。前轮消耗、突发额度和账号其他流量未被隔离，不能假定它是在完全恢复的配额状态下运行。

成功分布需和成功分母一起阅读：例如 2gb/c200 的 p50 为 2517.9 ms，但仅 **148/200** 成功；它不是 200 个请求都被接纳时的延迟分布。错误等待时间保留在原始事件中，不混入成功延迟，也不能用成功 max 代表所有失败请求的最坏等待。

## 本轮结论与适用范围

1. **完整覆盖了指定 15 格，但未实现全请求成功。** 正式 938/1083 成功、145 次新 session 速率限流。成功会话的 warm 跟测均通过；2gb/c1 只得到一次限流结果，没有可用的成功首调用基线。
2. **成功首调用中位数集中在约 2.4–2.9 秒，但不是通用性能保证。** 本轮同并发下的成功 p50 并未随镜像大小一致递增；这不能证明大镜像无成本，也不能从受限流筛选的成功分布推出扩展能力。应用不读取 padding，实际初始化负载很轻。
3. **高并发不是理想同时到达的流量。** 三档 c200 均出现限流，而且全部 c50 以上未达到 ≤100 ms 发送前跨度目标。进程隔离和全局屏障不等于网络或服务端同时接收。
4. **每格只有一轮，且准备条件并非完全等价。** c1 仅一个尝试；c10 尾分位数也只有少量成功样本支撑。固定顺序、账号共享配额、复用三格与新测的时间差、不同 smoke 等待时长，以及无法观测的缓存和调度状态，均为混杂因素。大量同轮请求不等于多次独立实验，不能据此建立 SLA、稳定吞吐或确定的并发性能曲线。

### “冷启动”命名的边界

本报告中的冷启动数据严格指**全新 session 的首次调用 E2E**。新 session ID 不会强制清空平台缓存，也不能证明发生了完整镜像拉取、microVM 创建或某种特定恢复流程。

响应中的进程时间戳及证据中的 `fresh_boots` 是应用层信息／启发式，不是平台提供的启动证明。一般而言，若系统恢复包含进程状态的快照，时间戳可能保留较早值；**这只是测量方法的通用限制，不是本实验确认了快照机制或认定它导致某项结果**。因此不按这些字段给请求贴“真实启动／预热命中”标签，也不从时间戳重复推断实例数量。

本轮没有追加请求来消除这些限制，也没有为获得全绿结果重试或更改配额。
