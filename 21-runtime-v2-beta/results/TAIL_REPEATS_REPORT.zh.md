# Runtime V2 长尾重复测试

日期：2026-09-13；区域：`us-west-2`；组合：500mb/c100、2gb/c200，各新增三轮。

## 结论

**重复测试支持“存在偶发长尾”，不支持“每轮都会稳定出现约 5 秒的 p99”，也没有确定 CPU 或服务端根因。**

- **500mb/c100**：三轮 p99 为 **4.349 / 3.503 / 3.044 秒**，max 为 **4.894 / 3.715 / 3.076 秒**。新增 263 个成功请求中，3 个超过 4 秒，均在第一轮；没有超过 5 秒的请求。原 p99 5.386 秒、max 5.525 秒的程度在三轮中未再出现，但不能据此保证不会再次出现。
- **2gb/c200**：三轮 p99 为 **3.479 / 3.519 / 3.467 秒**，max 为 **5.333 / 3.602 / 3.833 秒**。新增 566 个成功请求中，第一轮有一个 5.333 秒请求，**5 秒以上长尾再次出现**，但不是每轮都有。单个极慢请求可能不明显抬高 p99，max 和阈值计数仍需同时观察。
- 新增正式首调用共 **829/900 成功、71 次 HTTP 429**，没有其他首调用错误。成功请求全部完成 warm 和停止。延迟结论仅针对成功请求，不能忽略限流筛选。
- 六轮工作进程平均 CPU 核当量约 **0.92–2.68**，没有显示这些 worker 持续耗尽客户端 8 核；但没有逐核或线程调度采样，仍不能排除瞬时竞争。四个超过 4 秒的请求主要耗时仍位于 SDK 发送前钩子到响应返回之间，不能据此判定纯服务端耗时。

原多进程矩阵及其统计不改写、不与新增轮次合并；本文件是针对两个特定长尾组合的重复性实验。

核当量是全部 worker `cpu_seconds` 之和除以最早 client-ready 至最晚 worker-finished 的跨度，包含线程准备、首调用、warm、停止等；不是单请求 CPU，也不是整机逐核利用率。各 worker 的计时窗口也不完全相同。

**SDK 中间区间不等于 AgentCore 服务端耗时。** `before-send` 在传输前触发，其后包含连接获取、TCP/TLS、网络、服务端处理及客户端调度/响应解析；`response-received` 不是精确网络 TTFB。全局释放到调用开始不计入请求自身 E2E，不能把发起跨度直接从 p99 或 max 扣掉。

六轮发送前跨度约 **0.52–1.87 秒**，均未达到原客户端设定的 ≤100 ms 紧凑突发目标。虽然使用 8 个进程与全局屏障，仍不能把名义 c100/c200 解释为请求同时到达服务端。

## 方法、核验和限制

- **运行范围**：2026-09-13 13:49:14–14:11:56 UTC，各组合新增三轮，共 6 个独立临时 V2 Runtime；顺序固定为 500mb/c100、2gb/c200，重复三次。每轮重新启动 8 个 worker，不共享前轮的客户端或连接池。
- **工作负载保持一致**：使用原矩阵同一 image digest、区域、角色、PUBLIC/HTTP、idle 60 秒、maxLifetime 600 秒和 ping-pong payload；未更改冻结的多进程客户端与 recorder。每轮成功首调用立即 warm 再 stop，没有隔离 warm/stop 与其他未结束首调用的重叠。
- **间隔有所变化**：先完成六个 Runtime 的 smoke；最后 smoke 结束后等待至少 180 秒，再开始第一轮。之后从前轮测试流量全部完成起，至少等待 180 秒才启动下一轮；核验实际相邻流量间隔为 **180.395–180.527 秒**。各 Runtime 的 smoke 到其正式请求等待为 **235.215–1106.451 秒**，随着固定顺序延长。这并非六组相同 Runtime 年龄的随机对照。
- **间隔不是配额恢复保证**：新 session 配额仍为 25 TPS，数据面 1000 TPS，活跃 session 5000。只保证本测试没有在 quiet 窗口发送目标调用，无法排除账号其他流量或确认后台计量/突发额度已恢复。原矩阵的短间隔与本次不同，成功接纳样本也不同。
- **不重试、不丢样**：900 个正式尝试中 829 成功、71 限流，全部错误消息为 `New session creation rate exceeded`；没有其他首调用错误。829 次正式 warm 均成功。六次 smoke 也均完成首调用、warm、停止。
- **核验与清理**：含 smoke 共 **906 个唯一 session ID、2647 条 API 事件**（906 次首调用、835 次 warm、906 次停止）。835 次停止返回 HTTP 200，71 个限流会话的停止返回 `ResourceNotFoundException`。六个临时 Runtime 已删除，并于 14:12 UTC 独立只读确认不存在；镜像、IAM、原 Runtime 和原证据不变。
- **状态区分**：`measurement_complete=true`、`cleanup_complete=true`，但 `all_invocations_successful=false`，退出码 1 保留。完整记录通过核验，不将限流改写成成功。
- **未新增逐核 profiling 或网络抓包**：本次使用同一套 SDK hook 和整段 worker CPU 累计值进行重复性检查，未获得逐线程调度等待、TCP 重传或服务端 tracing。不能从重复测试确定 CPU 核数、网络或 AgentCore 哪一项为根因。
- **统计边界**：每个组合只有三次新增独立突发。每轮的多条请求并不是多次独立环境实验；没有超过 5 秒的观测不等于其真实发生率为零，不以这些样本宣称稳定 SLA。本次只说明在该协议下哪些长尾复现、哪些未复现。

原始证据：[`tail_repeats_2026-09-13/matrix.json`](tail_repeats_2026-09-13/matrix.json)，各轮文件由 `cells[*].folder` 定位。原先两个组合及其 evidence hash 单独保存用于对照。统计脚本会同时输出逐轮、按组合汇总的新增样本、原样本以及所有 >4 秒/每轮最大值/p99 支撑请求的分段数据。
