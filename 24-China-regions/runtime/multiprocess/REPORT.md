# 中国区 Runtime 多进程冷启动报告

Owner：River。测试日期：2026-09-22；以下时间均为 UTC。

按用户最终要求，正式结论收口到 **100 并发**，不再追加压测。
200 并发在该指令到达前已经结束，原始证据保留在附录，后续脚本默认上限已改为 100。

## 1. 结论与最终范围

此前 Runtime 的 100 次冷启动基线是串行请求，50 并发扩容是单进程多线程。
本轮改为两区各一台 8 vCPU EC2，每区使用 8 个独立 Python 进程发起突发请求。
1、10、50 并发连续三轮均成功；100 并发出现服务端新会话创建限流。
不能将本轮写成所有并发档均通过，也不能只依据成功请求的低延迟忽略失败。

- 50 并发三轮，每区合计 150 个冷请求全部成功：宁夏 P50/P99 为 **1.702 / 2.423 s**，北京 **1.690 / 2.375 s**。
- 50 并发暖请求 P99：宁夏 **220.807 ms**、北京 **202.799 ms**，均超过 200 ms；这是并发突发条件，不能沿用历史串行暖基线的通过结论。
- 100 并发连续三轮错误率：宁夏 **2.00%**、北京 **15.00%**。
- 冷却后独立 100 并发：宁夏 **99/100**、北京 **100/100**；成功请求 P99 分别 **3.003 / 3.192 s**。宁夏剩余一次失败仍是新会话创建限流。
- 失败统一为 HTTP 429 `ThrottlingException: New session creation rate exceeded`，SDK 重试关闭。
- 连续三轮 100 并发的客户端 before-send 时间差约 **181–187 ms**，超过 100 ms；8 vCPU 客户端仍有突发签名、连接及调度开销。

带 180 秒冷却间隔的独立诊断已完成，见第 5 节；不覆盖连续压测记录。
两台 8 vCPU EC2 已停止并保留，本轮每区 19 个临时 Runtime 及相关 ECR、运行角色、传输桶已删除。

使用 profile `agentcore_cn`、账号 `447150580482`。实例通过 IMDSv2、STS 实例角色和
`os.cpu_count()` / CPU affinity 验证区域、身份及 8 vCPU。管理工作站只部署、调度、下载和分析；
镜像构建、容器自测及全部计时 Invoke 在对应区域 EC2 完成。

应用沿用此前的标准库 HTTP echo，无 LLM、业务 I/O 或人工添加的大依赖。基础镜像内容、
应用源码、Dockerfile 保持一致。基础镜像由私有 S3 传入区域内，EC2 校验后离线构建。
此处参考 `21-runtime-v2-beta/multiprocess_coldstart_client.py` 的客户端设计；
未复制其美国区 500 MB 测试镜像，未设置 V2 平台选项。中国区 GetAgentRuntime 未返回
platformVersion，不能据此报告已验证 V2。参考源及应用摘要见 [reference.json](reference.json)。

具体方法：

1. 历史实际执行 1/10/50/100/200 并发，各三轮；本报告主表仅列至 100，200 放入附录。每轮使用独立、从未 Invoke 的 Runtime，READY 后至少等待 60 秒。
2. `multiprocessing` 使用 spawn；并发 1 使用 1 进程，其余使用 8 进程。每进程独立 boto3 Session/client，提前解析实例凭据，各线程统一屏障发令。
3. 所有冷请求结束后，再统一发起同会话第二次暖请求。暖阶段结束后统一 Stop；失败的冷请求跳过暖请求，其 Stop 返回 404 则记录为会话不存在。
4. 首次响应要求 request_index=1；第二次为 2，实例标记一致。实例标记在首次请求时生成，避免启动期 UUID 被平台快照复制。
5. `perf_counter()` 计时覆盖 SDK Invoke 至完整响应读完。保存 before-send、response-received、AWS RequestId。计时阶段不写文件、不发送结果 IPC。
6. 无请求自动重试；失败、长尾全部保留。nearest-rank 分位数按原始成功样本排序计算，失败数量及比例单独列出。
7. 原计划末尾另有 50 并发、处理函数停留 5 秒的验证，用于检查 handler 重叠，其延迟不进入无停留冷启动表。
8. 连续批次间没有额外冷却，仅有客户端重建和前一批完成的间隔；由此暴露累积的新会话创建限流。后续诊断另加 180 秒间隔。

冷启动表示新用户会话首次请求，不表示 AWS 预热池为空或物理机器从零启动。
`before-send` 是 SDK 传输前事件，不能称为网卡发包时间。客户端延迟包含区内网络、
SDK、TLS/连接和服务处理，不能直接归因为服务端纯启动时间。

失败原文：

```text
HTTP 429 ThrottlingException
New session creation rate exceeded
```

含附录 200 并发及后置 50 停留组的历史完整连续测试，宁夏共 275 个冷请求失败，
北京 357 个；均为上述服务返回的限流。只统计 1/10/50/100 三轮，失败数分别为 6 和 45。
后续暖请求未发现失败。Stop 的 404 与被拒绝的冷请求逐一对应，说明这些请求未产生可停止会话。
当前中国区 Service Quotas API 对 bedrock-agentcore 返回 NoSuchResourceException / 服务不可用。
因此只报告观测到的新会话创建限流，不推测其准确额度或令牌桶参数。
本轮也没有隔离同账号的其他调用流量，不能从这些批次反推出账号的准确可用创建速率。

## 5. 冷却 180 秒的独立诊断

每区使用新的 Runtime，批次之间在前一批完整结束后等待至少 180 秒。
50 并发组保留 5 秒应用停留，用于处理重叠验证；100 并发为无停留的冷启动测量。
完整原始诊断还包含已完成的 200 并发，放在附录。

| 区域 | 并发 | 冷成功/计划 | 错误率 | 成功冷 P50 (s) | 成功冷 P99 (s) | 暖 P99 (ms) | before-send 时间差 (ms) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 宁夏 | 50（停留 5s） | 50/50 | 0.00% | 7.152 | 7.693 | 353.767 | 25.018 |

两区独立 50 并发均 50/50 成功，客户端及应用 handler 重叠峰值均为 **50**，实例标记互异。
此组延迟包含故意添加的 5 秒停留，不纳入冷启动 SLO，也不直接减去 5 秒声称得到纯服务启动时间。

独立 100 并发：宁夏 99/100、北京 100/100。宁夏 1 个失败仍为 HTTP 429 新会话创建限流，
示例 RequestId：`12c23b9c-1859-4f0c-bdb3-1feb9e924332`。
冷却有助于区分负载节奏的影响，但这一次诊断不能证明任意 100 并发都可零失败。
同样，诊断中的暖 P99 仍高于 200 ms，不扩大串行暖基线的通过结论。
CSV：[isolated_up_to_100.csv](results/20260922/isolated_up_to_100.csv)。

首次追加诊断在上传 `isolated/progress.json` 时遇到 S3 AccessDenied；
这是压测准备的权限配置遗漏，发生在第一次 Invoke 之前。修复仅增加本轮传输桶
`isolated/*` 的 PutObject 权限，原失败目录归档；重跑前明确检查没有 cells 目录、
没有已完成批次且错误属于 PutObject AccessDenied。未覆盖或混入真实测量失败。
