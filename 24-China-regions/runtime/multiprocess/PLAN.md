# 中国区 Runtime 多进程冷启动补测计划

Owner：River。日期：2026-09-22。区域：宁夏 cn-northwest-1、北京 cn-north-1。

**最终范围调整：用户要求测试收口到 100 并发，不再追加压测。**
该指令到达时 200 并发已执行结束，原始证据保留为附录；正式结论聚焦 1/10/50/100。
manage.py 后续默认只创建不超过 100 并发的测试矩阵。以下原计划保留用于解释已产生的证据。

## 目的

此前每区 100 次冷启动基线是串行请求；50 并发扩容使用单进程多线程。
本轮参考 `21-runtime-v2-beta/multiprocess_coldstart_client.py`，改用 spawn
独立进程、各自 SDK 客户端、统一发令屏障，并记录 SDK 事件时间及 CPU 情况。

## 环境

- 使用 profile agentcore_cn，验证账号 447150580482。
- 每区新建一台 c6g.2xlarge：8 vCPU、16 GiB、ARM64，非 CPU 积分实例。
  EC2 DescribeInstanceTypes / AZ offerings 已确认两区有该规格。
- 新实例通过 SSM 管理，无 SSH 入站，IMDSv2，8 GiB 加密 gp3。
- 继续使用此前标准库 HTTP echo 应用及固定 Python 基础镜像。
  基础镜像文件仅从工作站传送；构建、容器验证及计时请求全部在目标区域 EC2 执行。
- 每个并发档、每个重复批次使用独立、从未调用过的临时 Runtime。
  READY 后至少等待 60 秒，不做预调用。记录平台版本，不假定与美国区 V2 相同。

## 测量

1. 并发档位 1、10、50、100、200，每档 3 轮。每区共 1,083 个冷会话。
2. 每档使用 min(8, concurrency) 个进程；每进程创建独立 Session/client，
   提前解析实例角色凭据，连接池容量为分配请求数的两倍。
3. 全部请求线程与主进程通过同一个跨进程屏障发起冷请求。
   计时覆盖 Invoke 到完整响应读取，关闭 SDK 自动重试，保留全部失败。
4. 冷阶段全部结束后，再统一发起各会话第二次暖请求。暖阶段也为并发突发，
   与历史单会话串行 500 次暖请求分开统计，不能直接替代 7.3 基线。
5. 记录首次请求序号 1、第二次序号 2、会话内实例标记一致、会话间标记唯一。
   不把可被快照复制的进程启动 UUID 当作实例唯一性证据。
6. 各轮报告 P50/P95/P99/max、错误率、真实进程数、API 起始时间差、
   before-send 时间差、客户端请求重叠峰值、进程 CPU/RSS、主机 CPU/steal。
   before-send 是 SDK 传输前事件，不是网卡发包或纯服务耗时。
7. 另用独立 Runtime 做一轮 50 并发、应用停留 5 秒的扩容验证，
   检查处理区间重叠；该组延迟不混入无停留的冷启动统计。
8. 使用 nearest-rank 分位数；3 次重复的合并分位数从原始样本计算。
   并发 1 只有 3 个样本，仅作校验，不宣称建立稳健的 P99 基线。

## 判定与报告

- 50 并发目标错误率 0%；100/200 是新增压力观察，不自动扩展原验收目标。
- 同时报告冷 P50 <3s / P99 <5s 的逐档比较；并发暖 P99 与 200ms 作观察性比较。
- 发令时间差目标 100ms；未达到时保留结果并注明压测端局限，不删异常样本。
- 冷启动表示新用户会话首次请求，不能证明平台预热池为空或物理机器从零启动。
- 两区原始记录、执行源码哈希、实例信息、请求 ID、清理审计放在
  `results/<run>/区域/`，结论写入本目录 REPORT.md 并链接总报告。

## 根据第一轮结果追加：新会话创建限流诊断

北京连续批次的 100/200 并发出现 HTTP 429，错误原文为
`New session creation rate exceeded`；之后的 50 并发停留组也受影响。
保留完整连续批次数据。为区分批次累积影响和单次突发能力，每区再创建
3 个独立 Runtime：50 并发停留验证、100 并发、200 并发。
首次请求仍等待 READY 至少 60 秒，后续批次在前一批完整结束后冷却至少 180 秒，
参考 21-runtime-v2-beta 的 settle 时长。仅补一轮诊断，不用它覆盖前三轮的失败。
Service Quotas 对此中国区内部测试服务返回不可用，不能推断具体额度数值。
