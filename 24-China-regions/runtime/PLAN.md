# AgentCore Runtime 中国区验证计划

日期：2026-09-21；账号：`447150580482`；profile：`agentcore_cn`；
区域：`cn-northwest-1`。

## 测试对象与计时口径

部署仅用 Python 标准库实现的 HTTP ping/echo 服务，遵守 AgentCore 的
`GET /ping`、`POST /invocations` 协议，不调用 LLM、不访问外部业务服务。
固定 ARM64 容器镜像并记录 digest、实际大小、Runtime 配置及版本。

主验收客户端放在 `cn-northwest-1`，优先使用临时 PUBLIC Code Interpreter
运行压测脚本，绑定只能调用本次 Runtime 的专用执行角色。这样避免本地工作站
到中国区的跨区域网络往返影响 `< 200ms` 热请求验收。
所有 AWS 客户端显式指定区域，不向远端复制本地 profile 凭证。

主指标为调用端单调时钟计量的 `InvokeAgentRuntime` 发出至完整响应体读取结束，
包含中国区 API 网络及服务开销。另记录响应头到达耗时、应用处理耗时。
SDK 自动重试关闭，不丢弃失败、不使用“成功重试”替代首轮。

每次响应返回首次业务请求生成的 `instance_id`、启动时进程 UUID、guest boot ID、
进程启动时间、请求序号和处理时间。
全新 session 必须是第 1 次业务请求且 `instance_id` 各不相同；
热请求必须保持同一个 `instance_id` 和连续请求序号。
全新用户会话不等于已证明平台没有预热池；无公开控制可以清空服务内部预热资源。

## 验证清单

| 编号 | 优先级 | 方法与样本数 | 通过标准 |
| --- | --- | --- | --- |
| 7.1 | P0 | 并发 1，100 个全新 session 的首次请求，逐个执行和停止。 | 完整响应延迟 P50 **< 3,000 ms**，样本完整且请求成功。 |
| 7.2 | P0 | 使用同一批 100 个新会话样本。 | 完整响应延迟 P99 **< 5,000 ms**，样本完整且请求成功。 |
| 7.3 | P0 | 单独创建暖会话，首次准备请求不计入统计；同一会话连续 500 次 echo。 | 确认进程未变化，完整响应延迟 P99 **< 200 ms**。 |
| 7.4 | P0 | 独立部署、从未调用的 Runtime，从 0 个用户会话同时发起 50 个新 session；每个处理函数停留 5 秒以观察实际重叠。 | 50/50 首次请求成功，错误率 **0%**；检查 50 个独立进程与响应区间重叠情况。 |

P50/P99 使用 nearest-rank：排序后第 `ceil(p × n)` 个样本。严格小于目标才通过。
100 个冷样本足以计算样本 P99，但不代表长期尾延迟保证。并发扩容阶段的 5 秒工作负载
只用于重叠验证，不混入前三项的空载延迟。

“从 0 扩至 50”验收定义为从 0 个用户会话扩至 50 个独立会话；
平台内部是否从 0 个物理实例启动，需要服务端遥测才能证实，报告会注明这一边界。

## 执行顺序与资源

1. 确认中国区 Runtime 控制面与账号身份；检查本地 Docker、SDK 及中国区 ECR。
2. 编写最小容器、压测客户端和部署/清理脚本，先本地验证 HTTP 协议及进程计数。
3. 创建带唯一前缀的 ECR 仓库、最小权限 IAM 执行角色；
   部署 baseline、scale 两个临时 Runtime，设置 60 秒 idle timeout 和有限 max lifetime。
4. 创建中国区 PUBLIC 压测沙箱及专用角色，通过角色凭证运行负载。
   先验证 STS 身份、SDK、区域和最小调用，再按 7.1–7.4 执行。
5. 下载逐请求 JSON、汇总统计、错误、请求 ID、实例识别信息，生成中文报告。
6. 停止所有本次会话，删除本次 Runtime、压测沙箱、自定义解释器、ECR 镜像/仓库、
   测试 IAM 角色和测试日志组；保留本地证据。

资源创建前保存名称和意图，创建后立即保存标识；中断后可根据台账继续清理。
仅操作本次创建的资源。测试会产生少量运行和镜像存储费用。

## 执行中调整

首轮观察到：69 个新 session 的业务计数均为 1，但启动时 UUID 和 guest boot ID
仅有两种值，启动时间也重复。这与平台复用预初始化快照相符，原先将启动 UUID
视为独立实例标记的假设不成立，不能据此认定扩容失败。

保留 `results/20260921-runtime/` 首轮原始记录。在 `app.py` 中增加首次业务请求时
才生成并保存在进程内的 `instance_id`，通过跨会话唯一、同会话保持及请求序号验证
会话执行状态的独立性。使用新镜像、新 Runtime 和
`results/20260921-runtime-v2/` 完整复测，目标阈值、样本数和计时口径保持不变。
启动时 process ID / boot ID 仍保留，作为预初始化状态复用的证据，不作为实例计数。

热请求 P99 151.128 ms；50 并发 0 失败，客户端及应用处理峰值重叠均为 50。
