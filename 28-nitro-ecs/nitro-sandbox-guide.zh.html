01

先理解：它解决什么问题？

Agent 会执行命令、读写文件、调用工具。我们希望一个用户的运行环境不要影响另一个用户。

普通容器像同一套房里的不同房间：它们共享宿主内核。Nitro Sandbox 给工作负载单独的轻量虚拟机和 guest 内核，由 Nitro Hypervisor 提供 VM 隔离，适合运行不可信代码、Agent 工具与多租户工作负载。但它不替代身份认证、权限控制或数据加密。

执行环境一个 task，一间房

ECS 一个 task 对应一个 sandbox。同 task 多个容器不是多个租户边界。

资源出口磁盘、网络、权限分开管

私有工作目录、独立 ENI / SG、最小权限 task role，分别约束文件、网络与 AWS 操作。

威胁模型隔离不总等于保密

想防 parent 读取敏感数据，还需要 confidential、证明核验与按测量值放钥。

DSH 是什么？本仓库使用原版 @deepseek-ai/dsh@0.2.2-rc.1，通过 dsh headless 运行 Agent。ECS 的 HTTP wrapper 每次 /invoke 都启动新的 DSH 子进程。
术语可以这样理解
Parent instance负责管理、设备与生命周期的父 EC2 实例，不是 guest 的操作系统。
Guest / sandbox运行你代码的轻量虚拟机，有自己的内核和内存。
VMM / Firecracker在 parent 上管理 guest 的监控程序；EC2 路线由你安装。
Task / task definitionECS 中的一次运行 / 运行配方，定义容器、资源、网络和隔离模式。
Capacity providerECS 容量供应配置；Managed Instances 根据它管理 EC2。
Attestation证明环境测量值的机制；配合策略核验身份与镜像，再决定是否释放密钥。
02

看图理解：parent 与 guest 的关系

不是“在普通 EC2 里再套一层 KVM”。Parent 和 sandbox guest 都由 Nitro Hypervisor 管理。

ECS 模式防护边界本教程
SHARED默认，不使用每 task 独立 Sandbox 隔离。不作为目标
ISOLATED_SANDBOX信任 parent；用独立 guest 内核隔离不同任务。已实现 ECS 示例
CONFIDENTIAL_SANDBOX把 parent 视为不可信；还需 attestation policy 与 KMS 核验后放钥。介绍边界，未部署实测

EC2 Firecracker 接口另有 enclave.direct_mode：默认 confidential；设为 true 时 parent 可以读写 guest RAM。不要把 EC2 direct 与 ECS isolated 当成同一个 API 枚举。需要分别按安全模型设计。

机密模式不是万能保险箱。Parent 仍可影响设备、调度与可用性。应用把明文写入 parent 可接触的存储，或未经核验就接收密钥，数据依然可能泄漏。它也不同于传统 Nitro Enclaves 的应用模型。
03

选路线：先 ECS，还是先 EC2？

选择项ECS Managed InstancesEC2 + Firecracker
适合谁已会 Docker，希望快速运行 DSH研究 guest 镜像、VMM 与低层行为
交付物ECR 镜像 + task definitionEFI-stub kernel + initrd + VMM 配置
你管理什么任务、IAM、网络、存储与容量策略父 OS、内存池、Firecracker、guest、网络与磁盘
谁管理父 EC2ECS 自动管理；不要手工停/终止它你管理自己的专用父实例
持久化外部 EFS / S3 / 数据库独立数据盘后端 + 外部 checkpoint
现有代码28-nitro-ecs/27-nitro-ec2/
首次上手：先跑 ECS 无模型磁盘隔离测试，确认部署与边界，再做真实 DSH 性能测试。需要对比 direct / confidential guest 启动时，再走 EC2 路线。

ECS 这项能力要求 Managed Instances；不是 Fargate，也不能用普通自管 EC2 capacity provider 的配置直接替代。不是任何 Nitro 系列实例、任何 ECS 运行方式都支持。

开始前：账号、网络和版本

本机终端 · 身份与工具检查

python3 --version
docker buildx version
会产生费用。Sandbox 本身没有额外 premium，但 EC2、EBS、ECR、Logs、NAT、EFS、Lambda 和模型调用各有费用；ECS Managed Instances 另有标准管理费。本 HTML 不会自动运行命令或创建资源。

背后的两个核心配置字段

以下是字段摘录，不是完整可提交 JSON；分别属于容量配置与 task definition，不能混成一次 API。完整实现见 configuration.py。

CreateCapacityProvider · 字段摘录

      "nitroEnclavesEnabled": true,

3构建镜像并注册任务

4先验证隔离，再测 Agent

本机终端 · 无模型调用的隔离测试

5核对实际模式并清理

Benchmark 记录 task、trustedExecutionSummary、新 boot_id 和宿主信息，并停止测试 task。任务还运行时，可从控制台取本次 ARN 检查：

本机终端 · 先填本次真实值，不用旧 ARN
REGION=us-east-1
CLUSTER=YOUR_LIVE_CLUSTER_NAME
TASK_ARN=YOUR_LIVE_TASK_ARN
aws ecs describe-tasks --region "$REGION" \
  --cluster "$CLUSTER" --tasks "$TASK_ARN" \
  --query 'tasks[].{Status:lastStatus,Isolation:trustedExecutionSummary.isolationMode}'

期望 ISOLATED_SANDBOX。停止很久的记录可能过期，要结合集群与容量状态判断。结束实验：

本机终端 · 在本次新实验目录执行

06

EC2 上手：自己管理 Firecracker 与 guest

统一使用 ARM64。父实例、内存池、VMM、guest 镜像都由你负责，与 ECS 路线互相独立。

版本条件：示例要求 AL2023 kernel 6.18，至少 6.18.51-120.162.amzn2023，Firecracker 1.18.0+，guest EFI-stub kernel；confidential 还需对应 DMB 支持。不是所有 Nitro 机型都支持；不要选 flex、metal 或启用 nested virtualization 的配置，以当前官方支持列表为准。

1创建自己的专用 parent

填好私有子网、安全组和 SSM instance profile。SSM 角色与网络通路需先就绪，无需开放 SSH。这里只操作自己创建的实验 EC2。

本机终端 · ARM64 专用父实例
REGION=us-east-1
SUBNET_ID=YOUR_PRIVATE_SUBNET
SG_ID=YOUR_PRIVATE_SECURITY_GROUP
INSTANCE_PROFILE=YOUR_SSM_INSTANCE_PROFILE
aws ec2 run-instances --region "$REGION" \
  --image-id resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-6.18-arm64 \
  --instance-type m7g.2xlarge \
  --subnet-id "$SUBNET_ID" --security-group-ids "$SG_ID" \
  --iam-instance-profile Name="$INSTANCE_PROFILE" \
  --enclave-options Enabled=true \
  --metadata-options HttpTokens=required \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=dsh-nitro-workshop}]'

INSTANCE_ID=YOUR_NEW_INSTANCE_ID
aws ssm start-session --target "$INSTANCE_ID" --region "$REGION"

记录返回的 ID，等待 EC2 / SSM online 后连接；本机可能需要 Session Manager 插件。若 AMI 参数或机型不被区域支持，先查询支持条件，不退回未知旧内核。

2配置内存池，重启一次

Parent EC2 · 不是本机，也不是 guest
sudo dnf install -y dracut nftables iproute kmod tar gzip xz curl
uname -r
sudo grubby --update-kernel=ALL --args='nitro_enclaves.mempool=8G@0'
sudo reboot

重新通过 SSM 连接后检查：

Parent EC2 · 重连后
sudo modprobe nitro_enclaves
sudo dmesg | grep 'nitro_enclaves: CMA pool'
ls -l /dev/nitro_enclaves
cat /sys/class/misc/nitro_enclaves/pcie_slots{,_total,_in_use}

8G@0 是启动时保留的示例 pool，不是每个 guest 自动分配 8 GiB。为 parent、设备 buffer 与多个 guest 留余量；guest RAM 总和不能简单顶满 pool。Slots 数量同样约束并发。

3安装 Firecracker 与 Node 24

Parent EC2 · 固定官方 release
VERSION=1.18.0
ARCH=$(uname -m)
curl -sSfL -o firecracker.tgz \
  "https://github.com/firecracker-microvm/firecracker/releases/download/v${VERSION}/firecracker-v${VERSION}-${ARCH}.tgz"
tar -xzf firecracker.tgz
sudo install -m755 \
  "release-v${VERSION}-${ARCH}/firecracker-v${VERSION}-${ARCH}" \
  /usr/local/bin/firecracker
firecracker --version

确认官方 release 来源，并按其发布信息核验制品。父机需要原生 Node 24 / npm，已有则跳过安装。ARM64 安装例子：

Parent EC2 · Bash，ARM64，校验失败停止
set -euo pipefail
NODE_VERSION=24.20.0
NODE_DIST="node-v${NODE_VERSION}-linux-arm64"
curl -sSfLO "https://nodejs.org/dist/v${NODE_VERSION}/${NODE_DIST}.tar.xz"
curl -sSfLO "https://nodejs.org/dist/v${NODE_VERSION}/SHASUMS256.txt"
awk -v archive="${NODE_DIST}.tar.xz" '$2 == archive' SHASUMS256.txt \
  | sha256sum --check --strict -
sudo tar -xJf "${NODE_DIST}.tar.xz" -C /opt
export PATH="/opt/${NODE_DIST}/bin:$PATH"
node --version
npm --version

摘要与包同源，主要验证下载完整性；更高供应链要求需核验发布签名。重连要重新设置 PATH，不混用 x86_64 Node 与 ARM64 DSH 原生插件。

Parent EC2 · 不复制历史制品或凭证

5做一次无模型启动测试

Parent EC2 · 比较两种 guest 模式

sudo python3 benchmark.py --rounds 1 --direct-mode --out results/first-startup-direct

Firecracker 配置长什么样？

结构示意，不能原样直接启动：路径、TAP、init 与网络要准备。Benchmark 已负责这些。enclave 走 Nitro Sandbox，不是普通 /dev/kvm。

Firecracker · 配置结构示意
{
  "boot-source": {
    "kernel_image_path": "/absolute/artifacts/vmlinuz",
    "initrd_path": "/absolute/artifacts/initrd.img"

  "machine-config": { "vcpu_count": 2, "mem_size_mib": 4096 },

07

磁盘：隔离、保密、持久化是三件事

“B 看不到 A 的文件”不等于“parent 看不到”，更不等于“task 停了还能恢复”。

ECS：默认临时卷配置

Task definition · 字段摘录，其他必需容器字段未展示
{
  "volumes": [
    { "name": "workspace", "host": {} },
    { "name": "tmp", "host": {} }
  ],
  "containerDefinitions": [{
    "name": "dsh", "readonlyRootFilesystem": true,
    "mountPoints": [
      { "sourceVolume": "workspace", "containerPath": "/workspace", "readOnly": false },
      { "sourceVolume": "tmp", "containerPath": "/tmp", "readOnly": false }
    ]
  }]
}

空 host: {} 不指定宿主共享目录。Bootstrap 设置 HOME=/workspace、DSH_HOME=/workspace/.dsh，应用用 UID 1000；根文件系统只读，工作卷与临时卷可写。不给 Agent privileged、Docker socket 或共享宿主路径。

存储项当前限制 / 注意事项
每 task ephemeral固定 20 GiB；镜像压缩/展开也占空间，不能用 ephemeralStorage 自由扩大。
Provider 实例数据盘默认 80 GiB，可配 30–16,384 GiB；是宿主容量，不是每 task 80 GiB，多 task 共享 IOPS / 吞吐。
每 task EBS不支持 configuredAtLaunch=true 的 task 独立 EBS。
EFS用于外部持久化；本仓库 EFS / confidential 均未部署实测。现行文档讨论 EFS 支持与保密风险。

ECS：用 EFS 保存工作文件

先创建加密 EFS、私有 mount targets 与租户 Access Point。2049 仅允许 task SG；启用 TLS / IAM authorization。Access Point 设 /tenants/tenant-a、UID/GID 1000、0700；task 的 rootDirectory 省略或设 /。

本机 · 新 ECS 实验目录内，只生成配置，不创建 EFS
python3 examples/persistent_efs.py --state state.json --tenant tenant-a \
  --filesystem-id fs-YOUR_ID --access-point-id fsap-YOUR_ID \
  --task-role-arn arn:aws:iam::YOUR_ACCOUNT:role/YOUR_TENANT_TASK_ROLE \
  --out generated/tenant-a

替换真实 ID / ARN。输出 task definition、client policy、filesystem policy、Access Point settings；审查后自行创建/应用资源、注册任务。生成器面向 ISOLATED_SANDBOX，生成成功不是挂载验证通过。

不要逐租户覆盖共享文件系统策略。输出 filesystem policy 是专用单租户示例，会拒绝其他 principal / Access Point、非 TLS 与 ClientRootAccess。共享 EFS 要统一审查所有租户映射。

TLS 在 guest 终止也不防 parent 使用自己的 IAM 身份旁路挂同一 EFS。EBS / EFS 服务端加密不等于对 parent 保密。防 parent 需应用先加密，并在 attestation 核验后才放解密密钥。不要沿用旧资料“confidential 一律不支持 EFS”的断言；当前组合仍需单独设计和验证。

  "drives": [{
    "drive_id": "workspace", "path_on_host": "/absolute/tenant-a.raw",

  }]
}

B 使用另一份文件。普通 ext4 同一后端不能交给两个 guest 同时写，也不在 guest 运行时由 parent mount 修改；停止/卸载与 flush 后再做一致性检查。Raw 文件留在 parent EBS 可供新 guest 重用，但 parent 能读写它；confidential RAM 保护不会自动加密磁盘明文。

08

可以保存 Sandbox 快照吗？

当前不支持。Nitro Sandbox 不支持 snapshot / restore、pause / resume 或 live migration。Parent 不能 hibernate；stop、reboot、terminate parent 会停止其 sandboxes。底层用 Firecracker 不代表普通 Firecracker snapshot API 能绕过限制。

要“下次接着干”，先区分：文件恢复、应用进度恢复，不是 RAM 与进程快照。

目标Workaround限制
保存工作文件ECS 挂回租户 EFS；EC2 重用一致数据盘后端；或版本化文件归档。只恢复文件，不自动恢复 DSH 会话。
接着完成任务保存消息、工具结果、文件清单和进度，重建 Agent 上下文。需应用实现；模型后续输出可能不同。
备份文件版本EFS backup、私有对象归档、外部卷数据备份。不是完整 Sandbox 快照；先保证写入一致性。
不重复初始化维持运行中的 task 池，按租户严格分配。持续计费、非暂停；故障/host 替换仍丢内存。

应用 checkpoint 设计示例

设计示例 · 不是 DSH 自带格式或已实现的 resume API
{
  "schema_version": 1, "tenant_id": "tenant-a",
  "session_id": "session-001", "checkpoint_id": "turn-0002",
  "dsh_version": "0.2.2-rc.1", "completed_turn": 2,
  "messages_ref": "private/messages/turn-0002.json",
  "workspace_ref": "private/workspaces/turn-0002.tar",
  "workspace_sha256": "REPLACE_WITH_VERIFIED_SHA256",
  "completed_operation_ids": ["tool-operation-001"]
}
  1. 在完整 turn / 工具操作结束时暂停应用写入，保存一致的文件与消息版本。
  2. 先写 immutable 数据，再用事务或原子指针发布 checkpoint；不能读到半份状态。
  3. 恢复先认证租户，校验版本、checksum、路径与解包安全，再加载文件和上下文。
  4. 重新获取短期凭证、建立网络；凭证、token、socket 不进入 checkpoint。
  5. 外部副作用用幂等 ID / 去重或人工核对。“外部动作完成、checkpoint 未保存”时不能盲目重做。
本仓库尚未实现会话恢复。每次请求 spawn 新 DSH；warm 是同 task 后续调用，不是长驻会话。保留 /workspace/.dsh 也不保证原生 DSH 自动续接；单独验证版本会话接口，没有接口时由应用显式传回消息与工具结果。

你应该记录什么

  • 固定环境：区域/AZ、实例、CPU/RAM、模式、内核、DSH/Node、image digest 与模型。
  • 证明真的冷：新 ARN / boot_id，容量是否零、镜像缓存是否命中；首请求前不预热 DSH。
  • 拆开时钟：客户端 submit→ready、ECS created→started、pull、DSH spawn→首文本；首 status event 不是首文本。
  • 报告正确性：回答、失败、超时、cleanup 状态；样本足够才有意义地报告 p50/p95。
  • 优化有边界：小镜像、热容量、减少重复初始化可降部分等待，但不是 snapshot；跨租户热 task 复用需清理数据与身份。

详见 ECS 实测报告 与 EC2 实测报告。生产性能请按自己的环境、样本量与成功标准重测。

现象先检查
CLI 未知字段CLI / API model 是否支持；不删 Nitro / isolation 字段来绕过报错。

RUNNING 但 /health 不通Task ENI、probe SG→task SG 8080、应用监听、CloudWatch 日志。
DSH AccessDenied / 无文本Task role、region/model 支持、出站、临时凭证与应用错误；HTTP 200 不等于成功。

Guest 内存 / slots 不足Pool、slots、已有 guests、parent/设备余量，不直接在生产机调整。

新 task 文件丢了是否临时卷？跨 task 保留需外部存储，不是增加宿主数据盘就会恢复。

ECS 换 AZ 的注意事项

历史 CLI 2.40.3 的 UpdateCapacityProvider 不接受 Nitro 字段，更新 launch template 后 describe 曾丢该开关，不把去掉字段再 update 当可靠迁移。move_capacity_az.py 用创建新 provider → 核验 → 切换专用 cluster → 删除旧 provider，只适用于没有运行/待启动任务的专用 demo，不是生产无损迁移方案。

清理，而不只是退出终端

ECS按 state 清理容量

新实验目录执行 python3 cleanup.py，核对 tasks 为零、provider 删除完成、probe 删除。

EC2只处理自己的 parent

退出实验 guest、保存结果。Stop 仍保留 EBS 费用；不用则核对 ID / 标签后 terminate。

数据保留项单独审查

ECR、Logs、EFS、EBS、备份与 NAT 等不因 task 停止自动消失。

ECS cleanup 保留 ECR image、Logs、IAM roles/profile、SG 与空 cluster，便于检查与重用。不是删除全部资源、完全无费用，也不删除共享 VPC / NAT。
