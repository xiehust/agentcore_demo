AgentCore Runtime / Gateway 无 VPC Egress 时的 Workaround 方案

假设 Bedrock AgentCore 在中国区（宁夏 cn-northwest-1 / 北京 cn-north-1）首发时，Runtime 与 Gateway 均未提供基于 VPC Lattice 的原生私有出站（VPC Egress），如何让 Agent 安全访问 VPC 内的私有资源（数据库、内部 API、自建 MCP Server）。

01概述

在全球商用区，AgentCore 已通过 Amazon VPC Lattice 为 Runtime 和 Gateway 提供了原生 VPC Egress（privateEndpoint / managedVpcResource），Agent 可直接、私有地访问 VPC 内资源。但新区域（尤其中国区）在服务首发时，往往先上线核心能力，VPC Lattice 集成、PrivateLink 等网络高级特性会滞后。

好消息是：访问私有资源并不强依赖 Gateway/Runtime 自身的 VPC Egress。AgentCore 的两种目标类型，即 Lambda target 和 API Gateway target，通过 AWS 骨干网调用，再由这些“中间层”进入 VPC，本身即规避了对原生 VPC egress 的需求。这是缺失 VPC Lattice 时最简洁、最推荐的路径。

✅ 结论 首选 Gateway → Lambda target（Lambda 挂 VPC）：开箱即用、无需任何 VPC egress 配置、流量走骨干网。其次是 Gateway → 区域型 REST API Gateway → VPC Link。这两条在中国区几乎必然可用。
✅ 已实测验证（2026-07-29，us-east-2） 方案一与方案二均已在真机上跑通：在一个刻意构造为零互联网出口的 VPC（无 IGW、无 NAT、路由表无 0.0.0.0/0）中，AgentCore Gateway 成功读取了私有 RDS MySQL（PubliclyAccessible=false）的真实数据。本文核心判断成立。

但实测同时发现文档原有的 API Gateway 资源策略写法存在安全问题（或无法收敛，或导致 Gateway 自身被拒绝），以及若干必填参数缺失。相关内容已就地修正，完整实测数据与勘误见 第 09 节 · 实测验证与勘误。

Private IdP 绕行方案（第 08 节）同样已实测通过（9/9）：在 AgentCore Identity 无法访问的私有 IdP 场景下，interceptor Lambda 绕行完整可用；过程中又发现 3 个官方文档未记载的行为，其中 1 条会让所有请求失败。

02关键概念辨析：区分 Egress 与 Ingress

讨论 workaround 前，先厘清两个方向，否则容易选错方案：

方向含义对应能力是否是本文重点
Egress（出站） Agent / Gateway 主动出去访问你 VPC 内的私有资源（RDS、内部 API、自建 MCP） VPC Lattice privateEndpoint；Runtime VPC 配置（ENI） ✅ 本文核心（假设中国区缺失）
Ingress（入站） 你 VPC 内的应用私有地调用 AgentCore 的 API（不走公网） Interface VPC Endpoint / PrivateLink 补充章节讨论
ℹ️ 为什么 Egress 是难点 Egress 要求 AgentCore 托管服务进入你的 VPC，底层依赖 VPC Lattice resource gateway 与 ENI 的编排能力，而新区域最容易缺失的正是该编排。Lambda 与 API Gateway 这类已部署于 VPC 内的中间层，使 AgentCore 只需通过公开或骨干网端点调用即可，从而规避对 egress 的依赖。

04方案一 · Lambda 桥接（首选）

AgentCore Gateway 原生支持 Lambda target，且官方明确：“This functionality is available out-of-the-box and requires no additional configuration”。Gateway 通过 AWS 骨干网直接 invoke Lambda，Lambda 本身挂载到你的 VPC（配置 subnet + security group），即可访问 RDS、ElastiCache、内部 API 等私有资源。

Agent → AgentCore Gateway  →(骨干网 invoke)→  Lambda(VPC-attached)  →  RDS / 内部API / 自建MCP

为什么它绕开了 VPC Egress

  • Gateway 到 Lambda 是 service-to-service invoke，不需要 Gateway 进入你的 VPC。
  • “进入 VPC”这一步由 Lambda 的原生 VPC 能力完成。该能力早已成熟，中国区完整支持。
  • 因此整条链路不依赖 AgentCore 的任何 egress 特性。

落地要点

  • Lambda 配置 VpcConfig（至少 2 个 AZ 的私有子网 + 安全组），放在能路由到目标资源的子网。
  • 把每个“工具”实现为 Lambda 里的一个处理分支，或一个 Lambda 对应一个工具；Gateway 会把工具 schema 暴露给 Agent。
  • Gateway 执行角色遵循最小权限：只允许 invoke 指定的 Lambda ARN，不要给宽泛的 lambda:InvokeFunction *。
  • Lambda 如需再访问 AWS 服务（S3/DynamoDB）且子网无 NAT，配 VPC Endpoint 即可。

优点：零 egress 依赖、开箱即用、流量私有、成本低、冷启动可控（Provisioned Concurrency）。

限制：受 Lambda 15 分钟超时/负载上限约束；长连接/流式 MCP 场景需评估；工具逻辑需封装进 Lambda。

✅ 实测结果 在无 IGW / 无 NAT 的 VPC 中跑通，端到端 p50 730 ms。硬证据：MySQL 自身 USER() 返回的来源地址是 agentadmin@10.30.11.161，即 Lambda ENI 在私有子网内的地址，表明查询确实从 VPC 内部发起。 Lambda 的 toolSchema 会被 Gateway 强制校验（把 limit 传成字符串会被 ValidationException 拦下）。

端到端（经 Runtime）：跑在 networkMode=PUBLIC、无任何 vpcConfig 的 Runtime 上的 Strands Agent，4 题全部命中 rdsLambda___* 工具，p50 1924 ms（1680–2197 ms）。写法见第 06 节。

05方案二 · API Gateway + VPC Link（首选）

官方文档明确了这条路径：“While direct VPC communication from the Gateway is not currently available … the gateway communicates with API Gateway over the AWS backbone … The API Gateway can then communicate with resources using VPC Link”。这正是为“没有原生 VPC egress”量身准备的官方模式。

Agent → AgentCore Gateway →(骨干网)→ REST API Gateway(区域端点) → VPC Link → NLB → 私有资源

落地要点

  • AgentCore Gateway 仅支持区域型（regional endpoint）REST API 作为直接 target。
  • API Gateway 通过 VPC Link（私有集成，后端为 NLB / 私有 ALB）进入 VPC。
  • 出站鉴权仅支持两种：IAM（SigV4，用 Gateway 执行角色） 或 API Key（Gateway 托管）；不支持 OAuth 和跨账号（跨账号/OAuth 请改用下面的 OpenAPI target）。实测确认
  • 必填：创建 target 时必须提供 apiGatewayToolConfiguration.toolFilters，白名单列出要暴露为工具的 path + method（详见 勘误 3）。
  • 用资源策略把 API Gateway 收敛到只有你的 Gateway 执行角色能调用。注意：必须按执行角色 ARN（aws:PrincipalArn）来写，不能按 aws:SourceArn 写 Deny，后者会导致 Gateway 自身被拒绝，实测已复现，见 勘误 1：
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAgentCoreGatewayRole",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws-cn:iam::ACCT:role/my-gateway-exec-role" },
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws-cn:execute-api:cn-northwest-1:ACCT:api-id/stage/*/*"
    },
    {
      "Sid": "DenyEveryoneElse",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "execute-api:Invoke",
      "Resource": "arn:aws-cn:execute-api:cn-northwest-1:ACCT:api-id/stage/*/*",
      "Condition": {
        "ArnNotEquals": { "aws:PrincipalArn":
          "arn:aws-cn:iam::ACCT:role/my-gateway-exec-role" }
      }
    }
  ]
}
⚠️ 本文早期版本给出的策略已被实测证伪 早期版本推荐 Principal = bedrock-agentcore.amazonaws.com + ArnEquals aws:SourceArn。 该 Allow 本身有效，但只写 Allow 并不能收敛访问（同账号会与身份策略取并集）， 而一旦补上对称的 aws:SourceArn 取反 Deny，Gateway 会被自己的策略拒绝。 请使用上面基于 aws:PrincipalArn 的版本。完整 6 组对照实测见 第 09 节。
⚠️ 中国区 ARN 注意 中国区分区是 aws-cn，不是 aws。所有资源策略/IAM 里的 ARN 都要写成 arn:aws-cn:...，且服务主体在中国区是否为 bedrock-agentcore.amazonaws.com 需在上线后以实际文档为准（中国区服务主体有时带区域后缀）。
✅ 实测结果 完整链路 Gateway → 区域型 REST API（方法鉴权 AWS_IAM）→ VPC Link → 内网 NLB → 私有子网 EC2 → RDS 跑通，端到端 p50 737 ms，与方案一基本持平。 硬证据：MySQL USER() 返回 agentadmin@10.30.11.109，即 EC2 的私有 IP。 收敛效果验证：无凭证直调 → 403 Missing Authentication Token；用账号内管理员身份 SigV4 直调 → 403 explicit deny；经 Gateway 调用 → 200 + 真实数据。

端到端（经 Runtime）：同一 Agent 指定该链路，获取到 EC2 私有 IP 10.30.11.109，1820 ms。但要留意勘误 9：该链路生成的工具会额外包含一个 basePath 参数，模型填充后返回 403。

私有 REST API 的变体（OpenAPI target）

若你的 API Gateway 是私有（private）REST API，不能直接做 target。官方 workaround：导出为 OpenAPI schema，作为 OpenAPI target 导入，并把 routingDomain 指向 API Gateway 的 VPCE DNS。但该步骤依赖 privateEndpoint 与 VPC Lattice，若中国区缺失，此变体不可用，请退回方案一。

06补充 · Runtime 侧：把出站下沉为工具

这一节不是第三条网络方案，而是 Runtime 侧的写法。方案一和方案二讲的是 Gateway 怎么进 VPC，这里回答另一个问题：Runtime 里运行的 Agent 代码本身要连私有资源，而 Runtime 没有 VPC 配置能力，该怎么写。它没有自己的数据路径，实现就是方案一或方案二，因此端到端验证也并进了那两节。

核心思路：不要让 Agent 直接出站，把“出站”下沉为一个工具

  • 下沉到工具层：把所有需要访问私有资源的操作，改造成通过 Gateway 工具（→ Lambda / API Gateway）完成（即复用方案一或方案二）。Agent 仅调用工具，不自行建立连接，这是最符合 AgentCore 设计范式的做法。
  • 逻辑外置到 in-VPC 计算：把重逻辑放到 Lambda / ECS / EKS（挂 VPC），Runtime 里的 Agent 仅做编排与对话，私有访问全部由 in-VPC 组件承担。
  • Runtime 出公网访问模型：Runtime 访问 Bedrock 模型等属于服务调用，通常走 AWS 网络，不需要你的 VPC egress；真正缺的是“进你 VPC”，用上面两招补齐。
ℹ️ 设计原则 AgentCore 的推荐范式为“Agent 逻辑轻量、能力由工具承载”。在缺少 Runtime VPC egress 时，将“访问私有资源”实现为由 Gateway 暴露的工具，是最自然且最具可移植性的方案。待中国区补齐原生 egress 后，仅需替换工具实现，Agent 代码无需改动。

07补充 · 入站（Ingress）方向的私有连接

若需求方向相反，即VPC 内的应用要私有地调用 AgentCore API（不走公网），则属于 Ingress，应使用 Interface VPC Endpoint（AWS PrivateLink）解决，与 egress 无关。若中国区连 PrivateLink 也未就绪，则临时经公网 + IAM/SigV4 调用 AgentCore API（走 HTTPS，鉴权严格），待 PrivateLink 上线后切换。

⚠️ 需上线后确认的中国区事项
  • AgentCore 各子服务（Runtime / Gateway / Identity / Memory）在 cn-north-1、cn-northwest-1 的具体可用性与 GA 时间；
  • VPC Lattice 集成、PrivateLink、支持的可用区列表是否随首发提供；
  • 服务主体名称、ARN 分区（aws-cn）、跨区域推理是否受限。
以上以中国区上线时的官方文档 / 控制台为准。

08补充 · AgentCore Identity 不支持 Private IdP 的 Workaround

Private IdP = 自建在你 VPC 内网、公网访问不到的 OAuth2 / OIDC 授权服务器（如 Keycloak、PingFederate 或其他 OIDC 兼容授权服务器）。AgentCore Identity 需要在两个方向访问它：

方向AgentCore 要访问 IdP 的什么用途原生配置位置
入站（Inbound） OIDC discovery（/.well-known/openid-configuration）与 JWKS 端点 拉公钥，验证进来的 JWT authorizerConfiguration.customJWTAuthorizer.privateEndpoint（Runtime / Gateway 均可）
出站（Outbound） token endpoint 用授权码或 client credentials 换下游访问令牌 OAuth credential provider 上的 privateEndpoint
ℹ️ 与 VPC Egress 同根同源 官方文档明确：Private IdP 的私有连接 “is established using Amazon VPC Lattice resource gateways and resource configurations, following the same pattern used by AgentCore Gateway VPC egress”（由 AWSServiceRoleForBedrockAgentCoreIdentity 服务关联角色代管 Lattice 资源）。

因此中国区若缺失 VPC Lattice，访问私有数据资源与连接 Private IdP 会一起失效。二者同源，workaround 思路亦相同：把“连接 IdP”下沉到能进 VPC 的中间层。

核心绕行点：interceptor Lambda

interceptor Lambda 是 Private IdP 缺失时的万能绕行点。它挂在你的 VPC 里，天然能私有访问内网 IdP，把“AgentCore Identity 是否支持 Private IdP”这个依赖彻底解耦。官方文档也把它列为 Private IdP 的替代路径：“you can use an interceptor Lambda function for inbound authentication and override the Authorization header in the interceptor Lambda for use with outbound auth”。

Agent →(带 JWT)→ Gateway →REQUEST interceptor Lambda(挂 VPC)→ 内网 IdP: JWKS / token →(验签通过/换到令牌)→ target

interceptor 有两类，每种最多各配一个，且目前只能是 Lambda：

  • REQUEST interceptor，在 Gateway 调用 target 之前执行，用于请求校验、改写、自定义授权。
  • RESPONSE interceptor，在返回调用方 之前执行，用于脱敏、改写响应。

入站绕行：在 interceptor 里自己验 JWT

不再让 AgentCore Identity 去拉内网 JWKS，而是把 Gateway 入站鉴权换成 AWS_IAM（或 NO_AUTH + interceptor），JWT 校验完全由 VPC 内的 REQUEST interceptor 完成：

  1. interceptor 从 mcp.gatewayRequest.headers.Authorization 取出 JWT（必须把 passRequestHeaders 设为 true，否则拿不到 headers）。
  2. Lambda 私有访问内网 IdP 的 JWKS 端点拉公钥（务必缓存，见下方注意事项），本地验签 + 校验 iss / aud / exp / scope。
  3. 校验不通过时，直接在输出里返回 transformedGatewayResponse，Gateway 会立即用该内容响应、不再调用 target，等于短路拒绝：
{
  "interceptorOutputVersion": "1.0",
  "mcp": {
    "transformedGatewayResponse": {
      "statusCode": 403,
      "body": { "jsonrpc": "2.0", "id": 1,
                "error": { "code": -32001, "message": "token rejected" } }
    }
  }
}

校验通过则什么都不返回（或只回 transformedGatewayRequest），请求正常流向 target。

出站绕行：两条路，优先第二条

  • (a) interceptor 改写 Authorization：interceptor 经私有网络调用内网 IdP 的 token endpoint（client credentials）获取下游令牌，并写入转发请求的 header。
    注意：官方 payload 示例里，HTTP target（AgentCore Runtime / passthrough）的 transformedGatewayRequest 明确带 headers 字段，而 MCP target 的示例只列了 body。因此“改写 Authorization”在 HTTP target 上为明确支持，MCP target 需先在目标区域实测确认。
  • (b) 让 VPC 内的工具 Lambda 自己拿令牌（推荐）：方案一已将 target 实现为挂载 VPC 的 Lambda，该 Lambda 本身即可私有访问 IdP，直接在工具实现里做 token 交换，根本不需要 AgentCore Identity 的 outbound OAuth credential provider，也就不需要 Private IdP 支持。改造面最小、依赖最少。

配置示例

// CreateGateway / UpdateGateway
"interceptorConfigurations": [
  {
    "interceptor": { "lambda": {
      "arn": "arn:aws-cn:lambda:cn-northwest-1:ACCT:function:my-jwt-interceptor" } },
    "interceptionPoints": ["REQUEST"],
    "inputConfiguration": { "passRequestHeaders": true }
  }
]

Gateway 执行角色需要 lambda:InvokeFunction，且仅授权该 interceptor 函数，不应使用通配。

落地注意事项

  • ⚠️ passRequestHeaders 会把 Authorization 明文交给 Lambda。官方明确警告：headers 含认证令牌与凭证，务必确认 interceptor 没有把它打进日志。
  • 必须幂等。官方说明 Gateway 在失败或超时时可能重试 interceptor，实现要能安全承受重复调用。
  • 缓存 JWKS 与令牌。interceptor 在每次 Gateway 调用时都会执行，每次都去拉一遍 JWKS 会把延迟和 IdP 压力放大；按 kid 缓存公钥、按过期时间缓存令牌，并利用 Lambda 执行环境复用。
  • 冷启动。加在关键路径上的 Lambda 冷启动会直接体现在工具调用延迟里，必要时配 Provisioned Concurrency。
  • 附带解除一项限制：官方限制“配了 privateEndpoint 的 target 不能用 NO_AUTH 入站，除非Gateway 上配了 interceptor Lambda”，可见 interceptor 在设计上即可承担鉴权职责。

如果 VPC Lattice 可用（对照参考）

原生做法是在鉴权配置里直接挂 privateEndpoint，不需要任何 interceptor：

"customJWTAuthorizer": {
  "discoveryUrl": "https://idp.internal.example.com/.well-known/openid-configuration",
  "allowedAudiences": ["my-gateway-audience"],
  "allowedClients": ["my-client-id"],
  "privateEndpoint": { "managedVpcResource": {
      "vpcIdentifier": "vpc-0abc123def456",
      "subnetIds": ["subnet-0abc123", "subnet-0def456"],
      "endpointIpAddressType": "IPV4",
      "securityGroupIds": ["sg-0abc123def"] } }
}

原生方式自身的限制（与是否中国区无关，迁移时同样要满足）：discovery URL 必须 HTTPS；IdP 必须使用公信 TLS 证书，否则要在前面放一个带公有 ACM 证书的内网 ALB；跨账号只有 self-managed Lattice 支持。

✅ 本节已实测验证（us-east-2，9/9 通过） 在一个 AgentCore Identity 无法访问的私有 IdP 场景下（IdP 无公网 IP、仅 Lambda 安全组可达、VPC 无任何出网路由），interceptor 绕行方案完整跑通：入站由 VPC 内的 REQUEST interceptor 拉私有 JWKS 验签，出站由工具 Lambda 自行 client_credentials 换令牌后查私有 RDS。

可复现代码、9 项验证矩阵与原始证据见 13-private-idp-workaround/。实测同时发现 3 个官方文档没写的行为，其中第 1 条会导致所有请求失败，已补充在下方。

其中最具说明力的是第 4 与第 9 个用例。用例 4 的令牌由第二把 RSA 私钥签发， 该私钥从未提供给 IdP，既然能被识别，表明验签使用的确实是 IdP 的公钥。用例 9 的 kid 在 JWKS 中并不存在，可反向证明 JWKS 确实自私有 IdP 获取。 用例 2 与 5 至 8 均携带合法签名，仅声明存在问题，表明校验并未止于签名层。

⚠️ 实测发现 1 · 放行时必须回显原始 body，否则请求全挂

MCP REQUEST interceptor 放行时，直观写法是不做修改、返回空对象：

{ "interceptorOutputVersion": "1.0", "mcp": {} }

实测：客户端收到 HTTP 200 + JSON-RPC Parse error - Invalid JSON format，请求根本到不了 target。更容易误判的是：此时 9 个负例全部正常（transformedGatewayResponse 短路路径没问题），只有放行路径是坏的，表现形式接近拦截逻辑存在缺陷。

✅ 正确写法把原始 JSON-RPC body 回显出来： 
{ "interceptorOutputVersion": "1.0",
  "mcp": { "transformedGatewayRequest": { "body": <原始 JSON-RPC body> } } }

官方文档里“原样透传就返回空对象”（{"interceptorOutputVersion":"1.0","http":{}}）是写在 HTTP target 的 RESPONSE interceptor 一节的，不适用于 MCP target 的 REQUEST interceptor。

⚠️ 实测发现 2 · passRequestHeaders=false 给的是空字典，不是缺失字段

关掉 passRequestHeaders 后，interceptor 收到的是 headers: {}，而不是没有 headers 这个键。于是：

if headers is None:      # ← 永远不成立，检测不到配置错误

会把配置错误伪装成“客户端没带令牌”。我们实测时正是先看到 missing bearer token，真实原因却是 passRequestHeaders 未启用，容易导致排查方向偏离。应按空值判断：

if not headers:          # ← 空字典也能捕获
    return deny(request_id, "interceptor cannot see request headers",
                "set inputConfiguration.passRequestHeaders=true")

实测发现 3 · NONE 入站 + interceptor 可以正常创建并工作

authorizerType=NONE 搭配 REQUEST interceptor 可直接创建，Gateway 正常 READY，且 Authorization 头能完整交给 interceptor。这点很关键：入站若换成 AWS_IAM，Authorization 会被 SigV4 签名占用，业务 JWT 就得改走自定义头。

但要清楚风险：NONE 意味着 Gateway 端点没有平台层鉴权，interceptor 成为唯一关卡。它一旦报错、超时或被误删，结果即为完全开放或全部拒绝。生产环境应为 interceptor 配置 Provisioned Concurrency 与告警，Gateway 执行角色只授权这一个函数，并考虑 AWS_IAM + 自定义头做双层。

✅ 绕行方案的一个意外优势：不受“公信证书”约束 原生 privateEndpoint 路径要求 IdP 的 discovery URL 必须 HTTPS 且证书必须公信（否则要加带公有 ACM 证书的内网 ALB）。走 interceptor 时这两条约束都不存在，因为 HTTP 客户端由你自行实现。实测 demo 的 IdP 即为纯 HTTP。内网短链路可以接受，但生产仍建议 TLS，只是不再被公信证书绑住。
ℹ️ 仍未验证的一点 上文出站方案 (a)“interceptor 改写 Authorization”在 MCP target 上本次未能验证：对 Lambda target 而言 HTTP 头不可观测（Lambda 收到的是工具入参，不是 HTTP 请求），构造不出干净的观测实验。由于方案 (b)（工具 Lambda 自行换令牌）已实测跑通并已解决出站需求，建议直接采用 (b)，不必依赖头改写。

勘误清单

⚠️ 勘误 1（安全）· Deny 绝不能用 aws:SourceArn 收敛，将导致 Gateway 自身被拒绝

本文早期版本与 AWS 官方文档 gateway-vpc-egress.html 给出的资源策略是：

{ "Principal": { "Service": "bedrock-agentcore.amazonaws.com" },
  "Condition": { "ArnEquals": { "aws:SourceArn": "<gateway ARN>" } } }

这条 Allow 本身是有效的。实测把执行角色身份策略里的 execute-api:Invoke 删除后，仅凭该资源策略 Gateway 仍返回 200，表明在该次授权判断中 aws:SourceArn 确实存在且等于 gateway ARN。

问题出在 Deny 上。由于勘误 2（只写 Allow 锁不住），收敛必须加显式 Deny；若顺着文档思路把 Deny 也写成 aws:SourceArn 取反，Gateway 立刻被自己的策略拒绝：

User: arn:aws:sts::ACCT:assumed-role/my-gateway-exec-role/gateway-session-e465e38c-...
is not authorized to perform: execute-api:Invoke ...
with an explicit deny in a resource-based policy

从报错可以看出机制：这次请求还会以 Gateway 执行角色的临时会话身份再被判定一次，而在那个上下文里 aws:SourceArn 是缺失的。IAM 的取反类操作符（ArnNotEquals、StringNotEquals）在键缺失时判定为 true，...IfExists 同样如此，于是 Deny 命中；而显式 Deny 永远优先于 Allow。

✅ 正确写法 Allow 与 Deny 都按执行角色 ARN（aws:PrincipalArn）来写。该键对 SigV4 调用者一定存在，且 assumed-role 会话会解析成裸角色 ARN。完整策略见方案二正文。
附带发现：只要资源策略里有针对执行角色 ARN 的 Allow，执行角色的身份策略就不再需要 execute-api:Invoke（实测删掉后仍能调通）；保留它无害，AWS 文档亦如此建议。

⚠️ 勘误 2（安全）· 只写 Allow 的资源策略不等于收敛

本文早期版本称“用资源策略将 API Gateway 收敛至 AgentCore 服务主体”。实测表明，同账号调用时 API Gateway 会对身份策略与资源策略取并集，因此账号内任何持有 execute-api:Invoke 的主体均可调用成功。以管理员身份直接 SigV4 调用，返回了 200 和完整 RDS 数据。必须补显式 Deny 才算真正收敛。

勘误 3 · apiGatewayToolConfiguration.toolFilters 是必填项（官方文档未提及）

apiGateway target 不能只给 restApiId + stage，否则直接报参数校验失败：

ParamValidation: Missing required parameter in
targetConfiguration.mcp.apiGateway: "apiGatewayToolConfiguration"

必须用 toolFilters 白名单列出要暴露的 path + method；强烈建议再配 toolOverrides 给工具起 Agent 友好的名字与描述，否则工具名由 API 结构自动推导，可读性很差。

"apiGateway": {
  "restApiId": "xxxxxxxxxx", "stage": "prod",
  "apiGatewayToolConfiguration": {
    "toolFilters": [ { "filterPath": "/orders", "methods": ["GET"] } ],
    "toolOverrides": [ { "name": "listOrders", "description": "...",
                         "path": "/orders", "method": "GET" } ]
  }
}

勘误 4 · Gateway 入站可以直接用 AWS_IAM，验证阶段不需要 Cognito

本文与多数示例都用 CUSTOM_JWT + Cognito。实测 --authorizer-type AWS_IAM 完全可用：用 SigV4 对服务名 bedrock-agentcore 签名，直接 POST 到 Gateway 的 MCP 端点即可完成 initialize / tools/list / tools/call。POC 与验证阶段可省去整套 IdP；生产环境仍建议 CUSTOM_JWT，以承载用户身份。

勘误 5 · 两处时序相关问题

  • IAM 传播：CreateGatewayTarget 会立即校验执行角色对 Lambda 的 lambda:InvokeFunction 权限。新建角色后马上创建 target 会失败（Gateway execution role lacks permission to invoke Lambda function），策略内容其实是对的，重试即可。
  • API Gateway 部署限流 + 策略生效延迟：CreateDeployment 限流很严（TooManyRequestsException），需退避重试；资源策略改完必须重新部署 stage，且实际生效还需等待约一至两分钟。本次首轮验证“应被拒绝”的场景时仍返回 200，轮询后才变为 403。写自动化校验时必须轮询，否则会得出错误结论。

⚠️ 勘误 6 · MCP REQUEST interceptor 放行时必须回显原始 body

放行时返回 {"interceptorOutputVersion":"1.0","mcp":{}}，客户端会收到 HTTP 200 + JSON-RPC Parse error - Invalid JSON format，请求根本到不了 target。 必须把原始 JSON-RPC body 回显在 transformedGatewayRequest.body 里。

为什么容易误判：此时所有拒绝用例（transformedGatewayResponse 短路）都完全正常， 只有放行路径异常，表现形式接近自研鉴权逻辑存在缺陷。官方文档里“返回空对象即原样透传”是 写在 HTTP target 的 RESPONSE interceptor 一节的，不适用于此。

完整说明与正确代码见 第 08 节 · 实测发现 1。

⚠️ 勘误 7 · passRequestHeaders=false 给的是空字典，不是缺失字段

关掉该开关后 interceptor 收到 headers: {}，而不是没有 headers 键。 于是 if headers is None: 永远不成立，配置错误会伪装成“客户端没带令牌”， 导致排查方向偏离（实测观察到的症状是 missing bearer token，真实原因是开关没开）。 应改为按空值判断 if not headers: 并给出可操作的报错。详见 第 08 节 · 实测发现 2。

勘误 8 · NONE 入站 + interceptor 组合可用，但 interceptor 成为唯一关卡

authorizerType=NONE 搭配 REQUEST interceptor 可以正常创建并工作， 且 Authorization 头会完整传递给 interceptor。此点较为关键，因为入站改用 AWS_IAM 时 该头会被 SigV4 占用，业务 JWT 必须改走自定义头。

代价：Gateway 端点不具备平台层鉴权，interceptor 一旦报错、超时或被误删，结果即为完全开放或全部拒绝。 生产请配 Provisioned Concurrency 与告警，执行角色只授权该函数，并考虑 AWS_IAM + 自定义头做双层。 详见 第 08 节 · 实测发现 3。

⚠️ 勘误 9 · apiGateway target 注入 basePath 参数，模型填充后返回 403

由 apiGateway target 自动生成的工具，其输入 schema 中会额外包含一个 basePath 字段，既没有描述也没有约束：

{ "type": "object",
  "properties": { "basePath": { "type": "string" },
                  "limit": { "type": "string" }, "status": { "type": "string" } } }

basePath 是管道参数，不是业务入参。手写客户端不传它没事，但模型看到就可能去填，填进去 URL 就被改坏：

Server URL parameter 'basePath' contains invalid character '/'
Client error: API request failed with status: 403 - {"message":"Forbidden"}

困难之处在于其不稳定：同一 Agent、同一提问，模型有时不填充即成功，有时填充后返回 403。本次最初验证方案二的 Runtime 端到端时链路连通，间隔一段时间后重跑则连续三次 403，排查方向极易被引向 IAM。

怎么分辨是不是权限问题

看 403 的响应体就够了：

响应体含义
{"Message":"User: ... is not authorized to perform: execute-api:Invoke ..."} 真的是 IAM 拒绝。大写 Message，带主体 ARN
{"message":"Forbidden"} 路径没匹配上。小写 message，没有细节

为确认该结论，本次还将 Runtime 执行角色一并加入资源策略的 Allow，403 依旧，由此排除权限方向。

✅ 解法（按推荐顺序）
  1. 在 system prompt 里明确禁止。实测加上一句 never pass a basePath argument 之后，连续三次调用全部成功，稳定获取 10.30.11.109。
  2. 面向 Agent 的工具优先用 Lambda target。它的 schema 来自你自己写的 toolSchema，完全可控。注意 toolOverrides 只能改名字、描述、path 和 method，改不了输入 schema。
  3. 若工具必须由 apiGateway target 暴露，在客户端侧把 basePath 从工具定义里剔掉再交给模型。

✅ 被实测证实正确的部分

  • Lambda target 的“开箱即用、无需额外配置”成立，挂 VpcConfig 即可访问 RDS。
  • apiGateway target 仅支持区域型 REST API，确认（API 仅接受 restApiId + stage）。
  • VPC Link 后端必须是 NLB，确认，REST API 的 VPC Link 不支持 ALB。
  • 出站鉴权只有 IAM / API Key 两种，确认，无 OAuth 选项。
  • 整条链路不需要 Gateway 进入 VPC，确认，VPC 无任何出网路由仍全程可用。这是本文最核心的一条判断。
  • interceptor Lambda 可以完全替代 Private IdP 支持，确认。入站 JWT 校验与出站令牌交换均可在 VPC 内完成， 9/9 验证通过，且 interceptor 温调用开销为 2 ms。这是第 08 节的核心判断。
  • 把私有访问下沉为工具（第 06 节），确认。12-strands-nova2-runtime/ 里的 Strands Agent 跑在 networkMode=PUBLIC 的 Runtime 上（无任何 VPC 配置），仍能经 Gateway 读到私有 RDS。
⚠️ 迁移到中国区时的额外注意
  • ARN 分区是 aws-cn，所有策略里的 arn:aws:... 都要改写。
  • 勘误 1 在中国区影响更大：中国区服务主体名有时带区域后缀，而实测表明正确写法根本不该依赖服务主体，应改用执行角色 ARN。该结论与分区无关，可直接沿用。
  • 本次用到的 S3 网关端点、SSM 接口端点、VPC Link、内网 NLB 在中国区均为成熟能力。

10选型建议（决策顺序）

  1. 默认选方案一（Lambda 桥接）：零 egress 依赖、开箱即用、流量私有、成本低。约 90% 的“工具访问私有资源”需求应从此起步。✅ 已实测
  2. 已有大量 REST 内网服务 → 方案二（API Gateway + VPC Link）：用区域型 REST API + VPC Link，统一治理、鉴权用 IAM SigV4。✅ 已实测务必按勘误 1用 aws:PrincipalArn 写资源策略。
  3. Agent 代码本身要私有访问 → 别去找 Runtime 的 VPC 配置：把私有访问下沉为 Gateway 工具，底下仍然走方案一或方案二，Agent 不直连。写法见第 06 节。
  4. 入站私有调用 AgentCore API → PrivateLink（就绪后），未就绪则公网 + SigV4 过渡。
  5. 用内网自建 IdP（Keycloak / PingFederate）→ interceptor Lambda：Private IdP 与 VPC Egress 同样依赖 VPC Lattice，缺失时把 JWT 校验放进挂 VPC 的 REQUEST interceptor，下游令牌交换交给工具 Lambda 自己做。详见第 08 节。
✅ 可移植性 上述方案均将“访问私有资源”封装为工具或中间层。待中国区补齐原生 VPC Lattice egress 后，可平滑切换至 privateEndpoint，Agent 逻辑无需改动，迁移成本较小。
