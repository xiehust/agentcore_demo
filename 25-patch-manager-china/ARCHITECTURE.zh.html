1. 设计目标与约束

1.1 目标

  • 接手值守中的"异常处理"：每批 75~100 台的补丁由 Patch Manager 执行；对失败、挂起、离线、预检不通过的实例自动诊断，能安全修复的就修复并以真实重跑验证，其余生成审批单交给值班人员。
  • 单台不阻塞整批：任何一台实例的补丁挂起、诊断卡死或 API 异常，只影响它自己。
  • 最小权限与内网：一个诊断会话只能接触一台实例、只能执行预先审核的 SSM 文档、只能在运维 VPC 内使用凭证；不提供任何公网入口。
  • 可接管、可审计、可学习：值班人员能在同一会话中接手；所有动作留痕；每次诊断沉淀为可复用的知识与经验。

1.3 核心设计原则

确定性交给托管服务

批量下发、速率控制、错误阈值都是 Patch Manager 原生能力；编排状态全部落在 DynamoDB，Lambda 无状态。

不确定性限定在单台

Agent 只处理一台失败实例，会话、凭证、配额、记忆上下文都以这一台为边界。

约束落在模型之外

每条安全约束都由代码钩子、IAM 或人工流程强制执行，不依赖模型遵守提示词。

2. 总体架构

数据流：① Step Functions 每 30 秒驱动一次编排 Lambda；② Lambda 经 bedrock-agentcore 终端节点为每台失败实例调用一个 Runtime 会话；③ Runtime 经 STS 终端节点进入业务账号 Spoke 角色，以 SSM 对单台实例执行允许列表文档；④ 状态与 STM 写 DynamoDB，LTM 读写 OpenSearch；⑤ 经 NAT 调用全球区模型；⑥ 值班人员经 Identity Center 与 VPC 内门户接管同一会话。

3.2 实例状态机

4. 批次编排

4.1 Tick：每 30 秒一次的心跳

  1. 轮询补丁中的实例：首次观察到 InProgress 时记录 inprogress_at；运行超过 patchTimeout，或从下发起超过 waveHardTimeout 仍未开始，只对这一台 CancelCommand 并标 PATCH_TIMEOUT。
    代码：orchestrator/handler.py#L231 _poll_one() · orchestrator/handler.py#L246 inprogress_at · orchestrator/handler.py#L247 patch_timeout · orchestrator/handler.py#L251 wave_hard_deadline
  2. 超时与未认领检查：诊断超过 agentTimeout 的实例先写 NEEDS_HUMAN、再 StopRuntimeSession；已派发但在 dispatchGrace 内未被 Runtime 认领的实例释放回队列，第 3 次仍未认领则转人工。
    代码：orchestrator/handler.py#L258 _check_agent() · orchestrator/handler.py#L316 _reap_stale_dispatch() · orchestrator/handler.py#L270 _release_dispatch() · orchestrator/handler.py#L35 MAX_DISPATCH
  3. 派发：可诊断状态的实例按 failed_at 先后排队；空闲槽位 = maxAgents − 进行中；派发前先条件写 dispatched_at（attribute_not_exists），重叠的 Tick 也不会重复调用。
    代码：orchestrator/handler.py#L364 failed_at · orchestrator/handler.py#L365 maxAgents · orchestrator/handler.py#L293 _dispatch() · orchestrator/handler.py#L298 attribute_not_exists
  4. 异常隔离：每台实例的处理独立捕获异常，连续 5 次出错转人工；Tick 本身不因单台失败而失败。
    代码：orchestrator/handler.py#L322 _safe() · orchestrator/handler.py#L34 MAX_HOST_ERRORS

4.2 预检（下发补丁之前）

  • SSM 在线：DescribeInstanceInformation（分页）；非 Online → UNDELIVERABLE，不下发补丁，直接进入诊断。离线实例若照常下发，命令会一直 Pending 直到截止时间。
    代码：orchestrator/handler.py#L182 ping_statuses() · orchestrator/handler.py#L206 UNDELIVERABLE
  • 根盘余量：以编排会话对在线实例执行 PatchDiagnose-Collect Check=disk，解析机器可读行 ROOT_FREE_PCT / ROOT_FREE_MB；低于阈值或命令本身失败 → PRECHECK_FAILED。根盘 100% 时 SSM Agent 无法执行任何文档，所以磁盘余量必须在补丁之前检查。
    代码：orchestrator/handler.py#L154 disk_precheck() · orchestrator/handler.py#L172 ROOT_FREE_PCT · infra/03_ssm_docs.py#L34 ROOT_FREE_PCT · orchestrator/handler.py#L212 PRECHECK_FAILED

4.3 熔断与兜底

  • canary 熔断：canary 波次有失败 → 批次置 halted；后续波次的实例标 SKIPPED_HALTED、不下发；已在诊断的实例照常完成；最终以 CanaryCircuitBreaker 结束。
    代码：orchestrator/statemachine.json#L35 CanaryGate · orchestrator/handler.py#L411 halt() · orchestrator/handler.py#L195 halted · orchestrator/statemachine.json#L64 CanaryCircuitBreaker
  • Abort：Init / Waves / Drain 任一步出错（Catch），或超过 batchTimeout → Abort：非终态实例转 NEEDS_HUMAN、停止仍在运行的会话、取消挂起命令 → Report → Fail（BatchAborted）。
    代码：orchestrator/statemachine.json#L66 Abort · orchestrator/handler.py#L383 abort() · orchestrator/handler.py#L375 batch_deadline · orchestrator/statemachine.json#L78 Aborted

5. Session 设计

  • 单实例单会话：runtimeSessionId = {batchId}-{instanceId}（不足 33 字符右侧补齐）。批量执行不在 Agent 中，因此不受单会话 8 小时上限约束；诊断上下文只包含这一台实例。
    代码：orchestrator/handler.py#L91 session_id()
  • 异步任务：入口校验归属并条件写认领后立即返回 accepted；诊断在后台线程执行，期间 add_async_task 使 /ping 返回 HealthyBusy，会话不会被空闲回收；结束时 complete_async_task。
    代码：agent/app.py#L218 load_ctx() · agent/state.py#L38 claim_for_diagnosis() · agent/app.py#L327 add_async_task · agent/app.py#L215 complete_async_task
  • 生命周期：空闲 600 秒、最长 7200 秒。单台诊断通常为分钟级，用完即释放 microVM。
    代码：infra/06_runtime.py#L58 lifecycleConfiguration
  • workload token：SigV4 调用必须带 runtimeUserId，容器才能拿到 workload token 并从 Token Vault 取 API Key。编排层固定使用 runtimeUserId=patch-orchestrator，因此调用方需要 InvokeAgentRuntimeForUser 权限，资源策略同时放行该 action。Runtime 自动创建的 workload identity 由服务管理，调用方不能为其换取 token。
    代码：orchestrator/handler.py#L428 runtimeUserId · infra/02_iam.py#L94 InvokeAgent · infra/06_runtime.py#L84 AllowOpsInvokers · agent/app.py#L84 get_workload_access_token
  • API Key 获取时机：workload token 只存在于请求上下文中，因此在请求线程内取 API Key，再交给后台线程使用。
    代码：agent/app.py#L321 model_api_key · agent/app.py#L79 model_api_key()
  • 人工接管：门户以值班人员的 permission set 角色、同一 runtimeSessionId、runtimeUserId=操作人 调用 mode=chat；Runtime 从 DynamoDB 恢复完整对话（与 microVM 是否存活无关）。runtimeUserId 不会以 HTTP 头传入容器，审计所需的操作人由门户放进请求负载。
    代码：orchestrator/handler.py#L468 portal_chat() · agent/app.py#L331 mode == "chat" · agent/app.py#L336 human_takeover · agent/app.py#L110 RepositorySessionManager

11. 会话隔离

  • 平台：每个 runtimeSessionId 一个 microVM（独立 CPU、内存、文件系统），结束后销毁。实测中 A / B 两个会话的文件与内存互不可见，StopRuntimeSession 后再调用得到全新 microVM。
    代码：orchestrator/handler.py#L538 isolation_test() · agent/app.py#L282 isolation_probe()
  • 注意：microVM 从同一个已初始化的快照启动，各 microVM 的 boot_id 与进程启动时间一致，不能用它们区分 microVM；隔离性以"状态不串"验证。
    代码：agent/app.py#L292 boot_id
  • 方案层 4 层：会话粒度为批次 + 实例；load_ctx 以 DynamoDB 校验实例分配给本会话、不信任 payload，护栏在每次工具调用前再校验；IAM 会话标签绑定单实例；STM 按 sessionId 分区，接管时 workload token 按操作人签发。
    代码：orchestrator/handler.py#L91 session_id() · agent/app.py#L218 load_ctx() · agent/guardrails.py#L93 session_id · agent/tools.py#L41 TargetInstance · agentmem/agentmem/stm.py#L18 SESSION# · orchestrator/handler.py#L478 user_id
  • 停止语义：StopRuntimeSession 之后 microVM 终止需要数秒，期间仍可能产生写入；因此编排层先把实例写成终态，再停止会话，由护栏的"实例已终态"检查拦截后续动作。
    代码：orchestrator/handler.py#L258 _check_agent() · orchestrator/handler.py#L383 abort() · agent/guardrails.py#L95 TERMINAL

14. 生产化路线

  1. 模型与合规：完成数据出境与模型评估，确定推理与向量模型；优先 VPC 内模型以去掉 NAT。
  2. 身份与门户：Identity Center 对接企业 IdP，按值班组分配 permission set；VPC 内门户实现审批与接管。
  3. 审批执行：审批通过后由独立角色的 SSM Automation 执行高危动作。
  4. 双区：北京与宁夏各部署一套运维 VPC、终端节点与 Runtime；Spoke 策略中的 aws:SourceVpce 列出两区终端节点。

  6. 记忆治理：KB 人工确认流程、proposal 定期复核、规模增长后重跑阈值标定；AgentCore Memory 在中国区可用后按 namespace 迁移。
  7. 可观测性：失败率、自动修复率、失败 → 派发延迟、诊断耗时、护栏拦截、召回命中率的 CloudWatch 指标与告警。
