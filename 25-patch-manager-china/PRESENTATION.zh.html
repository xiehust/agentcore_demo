02 技术概览

分工：确定性的交给 Patch Manager，不确定的交给 Agent

确定性

Patch Manager + Step Functions

  • 按 PatchGroup 标签跨账号发现实例，canary / main 分波次
  • AWS-RunPatchBaseline（Install / NoReboot），MaxConcurrency、MaxErrors 速率控制
  • 执行前预检、单台截止时间、波次熔断、并发上限
  • 全部状态写入 DynamoDB，任一实例可单独重驱
不确定性

AgentCore Runtime 上的诊断 Agent

  • 只处理失败的那一小部分实例（通常 5% ~ 10%）
  • 读事实 → 只读诊断 → 允许列表内修复 → 重跑验证 → 报告
  • 修不了：生成审批单，交给值班人员在同一会话里接手
  • 从每次诊断中学习，下一次同类故障更快
Agent 不承担批量执行，因此批次时长与 Runtime 会话 8 小时上限无关；单台诊断通常 2 ~ 7 分钟。

03 总体架构

为什么跨账号不需要打通网络

Agent 的所有操作都是 AWS API

  • SSM SendCommand、DescribeInstanceInformation、ListCommandInvocations……
  • 由实例上的 SSM Agent 主动出站拉取并执行
  • 与某用户现有 Patch Manager 的工作方式完全一致

因此

  • 运维 VPC 与业务 VPC 之间不需要 Peering、Transit Gateway 或任何入站规则
  • 新增业务账号只需部署一个 Spoke 角色 和几份 SSM 文档
  • Runtime 安全组只出站 443、无入站；访问 AWS 服务全部经终端节点

05 Q2 Session 与编排

为什么一台失败实例一个 Session

8 小时上限不再是约束

批量执行是 Patch Manager 的原生能力；单台诊断 2 ~ 7 分钟，生命周期空闲 600 秒 / 最长 7200 秒。

故障隔离

每个会话一个 microVM。某台诊断挂起、崩溃或超时只影响它自己，可单独 StopRuntimeSession。

上下文干净、可接管

会话 ID = {批次}-{实例}；模型不被其他实例输出干扰，值班人员直接用同一会话 ID 接管。
方案优点问题结论
单会话处理整批实现简单受 8 小时上限约束；一台挂起拖住整批；上下文互相污染；无法按实例接管不推荐
按 Target 分组，每组一个会话会话数少组内仍互相阻塞；分组本身就是 Patch Manager 已有能力不必要
批量交给 Patch Manager，每台失败实例一个会话隔离、可并发、可接管、可按实例重驱需要编排层控制并发与新建会话速率（已实现）推荐

05 Q2 Session 与编排

实测：哪台失败就先修哪台，不用等整批跑完

怎么读　每行一台机器，横轴是批次开始后的秒数：蓝 打补丁　灰 已发现问题、等待派发　橙 Agent 诊断修复　● 结束

传统做法：整波等待

要等这一波所有机器都跑完（图中红色虚线，第 553 秒）才开始处理失败的机器。最慢的那一台，决定了所有故障机的等待时间。

本方案：失败即处理

disk-full 第 102 秒预检就发现磁盘不够，第 265 秒已修好；rpm-lock 第 245 秒补丁失败，马上开始修，第 367 秒修好。都比整波等待早 5 ~ 7 分钟开始处理。

每台机器互不影响

repo-broken 的补丁卡住不动，只有它自己等到截止时间被取消再交给 Agent，其他机器照常推进。4 台故障机 3 台自动修好，1 台转人工。

05 Q2 Session 与编排

实测结果：5 台机器、4 种故障，各自怎么处理

机器人为制造的故障结果发生了什么
healthy无（作为 canary 先打补丁）补丁成功canary 成功后，其余机器才开始打补丁
disk-full根盘只剩约 3% 空间自动修好打补丁前的预检发现空间不够；Agent 清理软件包缓存、旧日志和大临时文件，再重跑补丁成功。约 2.5 分钟
rpm-lock有进程一直占着软件包锁，补丁装不上自动修好Agent 找出占锁的进程并释放锁，重跑补丁成功。这类问题可能复发，所以另附一张根治审批单交给人决定
repo-broken第三方软件源不可达，且输出里藏着诱导 Agent 做危险操作的文字自动修好补丁一直卡住，到截止时间只取消这一台；Agent 没有理会诱导文字，临时停用这个坏掉的软件源后重跑成功
ssm-offline机器上的 SSM Agent 被停掉转人工远程通道断了，Agent 无法操作这台机器；预检时就识别出来，25 秒内生成「重启 SSM Agent」审批单

"修好"要有证据

只有补丁真实重跑成功，系统才接受"已修复"；Agent 自己说修好了不算。

修不了就交给人

Agent 不硬修：能力范围外的情况生成审批单，写明原因和建议操作，值班人员可在同一会话里接着处理。

只能做允许的事

Agent 只能调用预先审核过的几份 SSM 文档，不能随意执行命令，也不能重启或停止机器。

06 Q3 自建记忆

长期记忆管线：写入三步，召回一步

信号摘要 + 双路候选

查询用真实报错，只保留含 error / fail / lock / space / repomd 等特征的行；KB 同时取 kNN（语义）与 BM25（字面）候选。

两道闸门

绝对闸门：余弦 ≥ 0.36 或 ≥ 2 个特征串字面命中；再在综合分（余弦 + 短语加分 + 未审核 ×0.85）上应用相对边距 0.15。

召回内容不是指令

整体包在 <recalled_memory> 中并声明"仅供参考"；读写两侧剔除指令性文本；记忆服务不可用时降级为无记忆诊断。

写入质量门：LLM 做判断，代码守底线

步骤LLM 负责代码强制（LLM 无法绕过）
① 提取生成 Episode 五要素与知识候选；signature 从现有词表选或写成 new:<名称>命令输出视为不可信数据；不含实例 ID、主机名、PID 等个体信息
② 反思生成对照相关片段与已有反思选择 add / update，更新置信度update 的 id 必须是本次提供的条目，否则按新增；与已有反思余弦 ≥ 0.85 的新增按合并处理；置信度裁剪到 0.1 ~ 1.0
③ 合并（仅 FIXED）对照相关 KB 选择 AddMemory / UpdateMemory / SkipMemory只有真实重跑成功才进 KB；关键词必须字面出现在补丁输出类工具结果中并排除通用样板；verified 条目永不被改写，只进入 proposal 等人工确认；新增 signature 不覆盖已有条目

阈值来自实测标定

KB 正确匹配余弦 0.39 ~ 0.57、错误匹配 ≤ 0.505 → KB 阈值 0.36 + 综合分边距 0.15；反思正确 0.36 ~ 0.62、错误 ≤ 0.27 → 阈值 0.35。标定脚本可随时重跑。

def report_result(status: Literal["FIXED", "NEEDS_HUMAN"], ...):
    """FIXED is only accepted after a successful rerun_patch."""
    if status == "FIXED" and guard.last_rerun_status != "Success":
        return ("REJECTED: FIXED requires a successful rerun_patch "
                "in this session. Rerun the patch or report NEEDS_HUMAN.")

    state.update_instance(ctx.batch_id, ctx.instance_id,
                          status=status, signature=signature, ...)

08 Q7 会话隔离

会话隔离：平台 microVM + 本方案 4 层约束

层实现
平台 microVM每个 runtimeSessionId 一个 microVM，独立 CPU / 内存 / 文件系统，结束即销毁
① 会话粒度runtimeSessionId = {批次}-{实例}，由编排层生成
② 归属校验入口从 DynamoDB 校验实例确实分配给该会话；护栏每次工具调用前再查一次
③ IAMSpoke 凭证只允许 instance/${aws:PrincipalTag/TargetInstance}
④ 记忆与身份STM 主键 SESSION#{sessionId}；接管时 workload token 按操作人签发
隔离专项实测文件标记内存数据
A1 会话 A 写入 secret-A无secret-A
A2 会话 A 再次调用A 的标记secret-A
B1 会话 B无只有 secret-B
A3 StopRuntimeSession(A) 后再调 A无空（全新 microVM）
容器环境变量中没有任何 AWS 访问密钥（env_has_aws_keys=false）；microVM 被替换后，对话仍可从 DynamoDB 按会话 ID 恢复。
