1. 摘要与结论速览

某用户目前用 Systems Manager Patch Manager、自动化脚本和 Kiro 辅助排查来执行补丁批次（每批 75~100 台），出现异常时依赖人工值守。本次验证的目标，是在 AWS 中国区用 Amazon Bedrock AgentCore 接手"异常实例的诊断与修复"这部分值守工作，并逐项回答某用户提出的问题（Q1~Q7）。

一句话方案 批量补丁仍由 Patch Manager 执行（波次、速率、错误阈值都沿用原生能力）；Step Functions 每 30 秒检查一次批次进度，哪台实例一失败，就立即为它单独开一个 AgentCore Runtime 会话。Agent 只能使用预先审核的 SSM 文档，凭证被 IAM 绑定到这一台实例；能修就修，修完必须真实重跑补丁成功才算修复，否则生成审批单交给值班人员，值班人员可以在同一会话里接着处理。

2.1 分工：确定性的交给 Patch Manager，不确定的交给 Agent

确定性 Patch Manager + Step Functions

  • 按 PatchGroup 标签跨账号发现实例，canary / main 分波次
  • AWS-RunPatchBaseline（Install / NoReboot），MaxConcurrency、MaxErrors 速率控制
  • 执行前预检、单台截止时间、波次熔断、并发上限

  • 只处理失败的那一小部分实例（通常 5%~10%）

  • 修不了：生成审批单，交给值班人员在同一会话里接手

3. 总体架构

为什么跨账号不需要打通网络 Agent 对业务实例的所有操作都是 AWS API 调用（SSM SendCommand、DescribeInstanceInformation、ListCommandInvocations 等），由实例上的 SSM Agent 主动出站拉取并执行，这和某用户现有 Patch Manager 的工作方式完全一致。因此运维 VPC 与各业务 VPC 之间不需要 Peering、Transit Gateway 或任何入站规则；新增业务账号只需部署一个 Spoke 角色和几份 SSM 文档。

4.2 出站：同一个 Runtime 进入多个业务账号（Hub-Spoke）

每个业务账号部署同一个 Spoke 角色。Runtime 为当前会话负责的实例做 AssumeRole，并带上会话标签 TargetInstance=<该实例>；Spoke 权限策略使用 IAM 策略变量 ${aws:PrincipalTag/TargetInstance}，使这份凭证只能作用于这一台实例。编排 Lambda 使用不带该标签的会话，只能作用于带 PatchGroup 标签的实例。
