01项目概述与来源

本项目是由 AgentCore CLI 的 agentcore export harness 命令从托管 Harness 配置 （agentcore/app/myresearchagent_myresearchagent/harness.json）导出生成的自托管 Agent 应用。 导出的目的是把原本运行在 AgentCore 托管 Harness 上的 Agent，转换为一份可以自行修改、部署到 Bedrock AgentCore Runtime 的 Strands SDK 代码工程。

核心特征：

  • 入口为 main.py，通过 BedrockAgentCoreApp 的 @app.entrypoint 装饰器暴露为 Starlette ASGI 服务（流式 SSE 输出）。
  • 模型为 xai.grok-4.3，经由 Bedrock Mantle 的 OpenAI 兼容端点（/openai/v1，Responses API）调用，而非 Bedrock Converse API。
  • 内置三个本地工具（代码解释器、shell、文件编辑器）+ 一个远程 MCP Server（AWS Knowledge）。
  • 带有迭代次数 / 超时双重执行限制，以及滑动窗口对话管理。
⚠ 导出说明（EXPORT_NOTES.md） 浏览器工具（browser tool）依赖 Playwright Node 驱动，在 CodeZip（Lambda 风格）运行时无法执行， 因此被排除在本次导出之外。如需浏览器能力，需以 --build Container 重新导出。

04main.py — 应用入口与事件循环

4.1 Agent 装配（单例模式）　main.py:142-163

get_or_create_agent() 使用模块级全局变量 _agent 实现进程级单例： 同一个运行时容器内的多次调用复用同一个 Agent 实例，因此对话历史在容器存活期间天然延续（AgentCore 按 session 路由到同一容器，这就是会话连续性的实现方式）。装配参数：

4.2 payload 归一化　main.py:166-176

_extract_prompt() 接受三种输入形态，这正是它能承接 Harness 风格客户端工具循环的关键：

  • {"messages": [...]} — 完整消息数组，直接透传；
  • {"tool_results": [...]} — 客户端侧工具执行结果，被封装为一条含 toolResult 块的 user 消息回传给模型（续接上一轮的 toolUse）；
  • {"prompt": "..."} — 普通字符串提示词。

4.3 双层超时 + 优雅终止　main.py:220-255

超时控制有两层，语义不同：

  • 异步看门狗（invoke 内）：每次调用启动一个 3600s 的 _timeout_watchdog 任务，到点调用 agent.cancel() 硬中断流，随后补发 {"messageStop": {"stopReason": "timeout_exceeded"}}；finally 中保证看门狗被取消回收。
  • Hook 检查（模型调用前）：ExecutionLimitsHook 在每次模型调用前检查迭代数与耗时，超限抛 EventLoopException(ExecutionLimitExceeded)，被 invoke 捕获后同样转化为自定义 stopReason 返回 —— 客户端拿到的是正常流结束事件而非 5xx。

4.4 Skills 装载（当前为空）　main.py:206-213

⚠ 导出器缺陷的规避 Harness 配置中声明 skills=[]，但导出器曾硬编码一个默认的 anthropics/skills.git 源 —— 该仓库根目录没有 SKILL.md，导致每次调用都在 skill 解析阶段硬失败。 代码中已手工把 git_skill_sources 置空（main.py:207-210 的注释记录了这一决策），与 Harness 的实际配置保持一致。

4.5 死代码（导出模板残留）

_INLINE_FUNCTION_NAMES 恒为空集合，_has_inline_function_call()（main.py:179）与 _is_inline_function_call()（main.py:191）定义后从未被调用——它们是导出模板为"内联函数工具"预留的钩子，本 Harness 未配置该特性，属于可安全删除的残留。同理 _code_interpreter_id 依赖的环境变量未设置时走无参默认路径。

4.6 事件过滤　main.py:232-240

流出前做两道过滤：只透传形如 {"event": ...} 的字典事件；丢弃 start 为空的 contentBlockStart（Mantle/Responses API 流中会出现的空占位块），保证下游消费者看到的事件流干净一致。

06model/ — Grok via Bedrock Mantle

6.1 load.py — 实际使用的模型加载器

def load_model() -> OpenAIResponsesModel:
    region = os.environ.get("AWS_REGION", ...)
    token = provide_token(region=region)          # aws-bedrock-token-generator：短时效 Bearer token
    base_url = f"https://bedrock-mantle.{region}.api.aws/openai/v1"
    return OpenAIResponsesModel(
        client_args={"api_key": token, "base_url": base_url},
        model_id="xai.grok-4.3",
        params={"store": False},                 # Mantle 不持久化 responses，必须关掉服务端存储
    )

要点：

  • Grok 不走 Bedrock Converse API，而是走 Mantle 的 OpenAI 兼容端点（/openai/v1，Responses API 而非 Chat Completions）。
  • 鉴权用 aws_bedrock_token_generator.provide_token() 生成的短时效 Bedrock Bearer token 充当 OpenAI API key —— 底层是 SigV4 预签名，因此执行角色需要相应的 bedrock:InvokeModel* 权限。
  • store: False：Mantle 不支持 Responses API 的服务端会话存储，必须显式关闭，否则请求被拒。
⚠ Token 生命周期隐患 provide_token() 只在 load_model() 时执行一次，而 Agent 是进程级单例（§4.1）—— 即 token 与容器同寿。若容器存活超过 token 有效期（默认约 12 小时），后续模型调用将以 401 失败。 长会话/长驻场景应改为在每次请求前刷新 token（如自定义 httpx auth 或在 invoke 内重建 client）。

6.2 mantle_compat.py — 未被使用的兼容层

MantleCompatResponsesModel 继承 OpenAIResponsesModel，重写 _format_request_messages：把 assistant 消息的 content 数组（output_text 块） 压平为纯字符串。这是针对 Mantle 开源模型路径（/v1，gpt-oss-*）的 Pydantic 校验限制的 workaround。本导出使用的是专有模型路径 /openai/v1，load.py 用的是原生 OpenAIResponsesModel，此文件当前不参与任何执行路径——保留是为了切换模型时可直接复用。

07mcp_client/ — 远程 MCP 集成

结构极简（16 行）：get_aws_knowledge_mcp_client() 通过 streamablehttp_client（Streamable HTTP 传输）连接公开的 https://knowledge-mcp.global.api.aws，无需鉴权；get_all_remote_mcp_clients() 是聚合入口，返回非空客户端列表，供 main.py 逐个追加进 tools。

Strands 的 MCPClient 传入的是工厂 lambda 而非连接实例——连接在 Agent 使用时才惰性建立， MCP Server 暴露的工具（AWS 文档搜索/阅读等）在运行时动态发现并注入模型的工具列表。这赋予该 "research agent" 检索 AWS 官方知识库的能力，是其研究能力的主要来源。

08skills/fetcher.py — Skill 拉取与缓存

这是代码量最大（279 行）、工程质量最高的模块：负责把 Harness 声明的 S3 / Git skill 源下载到本地， 校验 SKILL.md 后交给 AgentSkills 插件。注意：当前 Harness 配置 skills 为空， 此模块在本部署中实际不会执行下载逻辑，但它体现了导出器的完整能力。

8.1 缓存设计

  • 缓存根：<tmpdir>/.agents/skills/{s3,git}/ —— 选 tmp 是因为 CodeZip 运行时工作目录（/var/task）只读；
  • 以源 URI 的 SHA-256 前 12 位作 key，.map.json 维护 hash → 目录名映射；命中即直接返回，首次调用后零网络开销；
  • 下载先落到以 hash 命名的临时目录，校验通过后 rename 为 SKILL.md 中声明的 skill 名（重名时追加 hash 后缀），任何失败路径都 _cleanup 删除半成品，保证重试不见脏状态。

8.2 两条获取路径

8.3 失败语义：fail-fast

resolve_s3_skills / resolve_git_skills 对任何单个源的失败都直接抛异常、令整次调用失败—— 注释写明理由："部分 skill 集会让 Agent 在缺失 Harness 声明能力的状态下静默运行"。这是一个正确的 完整性优先设计，也正是 §4.4 中导出器硬编码坏源导致每次调用必挂的原因。

09hooks/execution_limits.py — 执行限制

ExecutionLimitsHook 实现 Strands 的 HookProvider 接口，注册到 BeforeModelCallEvent（每次调用模型前触发），依次检查三项限制，超限即抛 EventLoopException(ExecutionLimitExceeded)：

限制本部署配置判定逻辑
最大迭代数75每次模型调用计数 +1，超过阈值终止（防止工具调用死循环）
超时3600stime.monotonic() 相对 Hook 构造时刻的耗时
最大输出 token未启用读取 event_loop_metrics.accumulated_usage["outputTokens"]
⚠ 计时/计数基准与单例冲突 _start_time 与 _iteration_count 都在 Hook 构造时初始化，而 Hook 随单例 Agent 只构造一次 —— 因此这两个限制实际是容器生命周期累计值，不是"每次调用"的限制： 容器启动 1 小时后（哪怕一直空闲），任何新调用的第一次模型请求就会命中 timeout；多次调用的迭代数也会累加、 逐渐逼近 75。对短生命周期容器影响不大，但长驻/高复用场景应把限制状态改为 per-invocation 重置 （例如在 invoke 中每次新建 Hook，或监听 invocation 开始事件重置计数）。

11已知问题、风险与改进建议

12总结

myresearchagent_myresearchagentAgent 是一份结构清晰的 AgentCore Harness 导出工程： main.py 负责装配与流式生命周期，model/、mcp_client/、 skills/、hooks/ 各司其职。其能力画像是——以 Grok-4.3（经 Bedrock Mantle OpenAI 兼容端点）为大脑，配备代码解释器、shell、文件编辑三个本地工具和 AWS Knowledge MCP 检索工具，在 75 次迭代 / 1 小时的双重限制下串行执行工具循环，并将全过程以 SSE 事件流回传。

代码整体质量良好，防御性细节（fail-fast skills、路径穿越检测、凭据保护、优雅终止）到位； 主要改进空间集中在单例生命周期带来的三个副作用（token 过期、限制计数累计、skills 只装配一次） 以及占位系统提示词。若计划长期运行或扩展 skills，应优先处理 §11 前两项。
