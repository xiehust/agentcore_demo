## 两类群体:真实微VM启动 vs 预热实例

## 部署后的首次调用

UpdateAgentRuntime 之后的第一次调用(500mb smoke,06:04 UTC)是一次真实启动,耗时 7,404 ms。约 3 分钟后完整矩阵开跑时,所有并发 1 的探测都已命中预热实例——AgentCore 会在部署后的几分钟内补充预热池。当流量超过预热池容量时,请按上表的真实启动延迟做容量规划。

## 测试方法

- 冷启动 = 使用**全新 40 字符 `runtimeSessionId`**(按 AgentCore 的 session 模型对应新微VM)调用 `InvokeAgentRuntime`,从发起 API 调用到完整读取响应体的客户端墙钟时间。boto3、SigV4、us-west-2,从同区域的 EC2 实例发起。
- **关闭** botocore 重试(`total_max_attempts=1`)——限流/错误被单独计数,绝不会被悄悄重试而混入延迟分布。读超时 300 秒。
- 并发 N:N 个线程通过 `threading.Barrier` 同时释放。
- 每档并发的样本量:并发1:每镜像 10 个样本, 并发5:每镜像 20 个样本, 并发10:每镜像 20 个样本, 并发50:每镜像 50 个样本;共 300 次探测。轮次间暂停 5 秒。后续运行新增的格子按“每个(镜像,并发)取最新原始文件”合并。
- 每次冷探测之后:同 session 做一次 warm 调用,然后(尽力而为地)调用 `StopRuntimeSession`。Runtime 均设置 `idleRuntimeSessionTimeout=60`。
- 填充层为 `/dev/urandom`(不可压缩),≤500 MB 分块,因此 ECR 压缩大小 ≈ 未压缩大小,拉取成本与标称大小一致。

## 注意事项

- **平台 2048 MB 上限:** AgentCore 拒绝 ≥2048 MB 的镜像(Service Quotas:“Maximum size for a Docker image in an AgentCore Runtime”),因此“2GB”变体实际为 1,950 MB。
- **预热池大小不透明**,可能随 runtime、账号、区域和时间变化;某并发度下的真实启动占比并非平台承诺。各格子的测量时间也不同(c=5 为后续补测),池状态存在差异。
- 平台侧镜像缓存可能使稳态启动快于部署后的最初几次启动;本次各轮启动耗时稳定,但这只是单日、单区域的快照,不构成 SLA。
- 离群值:一次 1gb 并发50 的启动耗时 39.6 秒(整个矩阵中仅出现一次)。

## 结论

1. **镜像大小决定真实冷启动延迟**:p50 8,121 ms (500mb) → 11,428 ms (1gb) → 13,503 ms (2gb)——与镜像拉取主导启动时间一致(压缩后每增加约 0.5 GB,冷启动约增加 2–4 秒)。
2. **并发几乎不拖慢单次启动**(各镜像的真实启动 p50 在不同并发下基本稳定);并发决定的是多少请求未命中预热池:并发1:0%;并发5:25–30%;并发10:55–60%;并发50:82–86%。
3. **限流不是问题**(300 次探测中仅 1 次限流;配额为每 agent 200 req/s)。
4. **Warm 请求稳定在 ~70–100 ms**,与镜像大小无关——微VM一旦就绪,镜像大小即无关紧要。
5. 实践建议:生产镜像尽量小(压缩后每 ~500 MB ≈ +2–4 秒冷启动);预热池只能掩盖低并发突发的冷启动(每 runtime 约 ≲5 个同时新建的 session)。
